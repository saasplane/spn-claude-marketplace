Instruments, not rules.

The plugins that carry SaaS Plane's rules into a running session, and the machinery that reads them.

This is the public marketplace that ships the instruments of the SaaS Plane agent — the plugins, and the machinery that reads their rules and runs them while somebody is working. Read this page to see how the pieces fit together before you open any one of them. Each area below links to the page that explains it in full.

Overview

The foundation book states the rules; this repository delivers them. Every rule here restates a chapter written somewhere else, and a rule invented here is a defect. It ships three plugins carrying five kinds of instrument in all.

A SaaS Plane workspace loads its agent instruments from here. They are hooks that fire on an event, tools somebody runs by name, skills that carry a stage's steps, refs that restate a chapter of the foundation book, and the agent briefs a session convenes.

What makes this repository unusual is what it is not allowed to be. It holds no rule of its own. A rule true of every repository belongs in the foundation book, and a copy kept here would be a second source that drifts away from the first. So every file that carries a rule names the chapter it restates, and a checker compares the two.

What is genuinely this repository's is not the rules but the machinery: the code that reads them, the events it runs on, and the shape each instrument takes.

Each section below expands one section of CONCEPT.md, under the concept's own headings and in the concept's own order. It stops well short of the concept's depth, and where the two differ the concept is right.

Boundary

The instruments themselves, as code and as files a runtime loads — and nothing about what those instruments say.

Who it serves

Two readers hold different halves of the same chain, and the difference decides how every page here is written.

ReaderWhat they holdWhat follows for them
The partner this repository, and not the foundation book every citation they meet here names a chapter rather than linking to one, and a ref carries enough of that chapter to be read in full without the book
The builder both trees, side by side in one workspace the drift checker is theirs. It is the only thing in the workspace that reads across the two trees, and it is run here, before anything is published: node packages/plugin-spn-devex/src/dist/cli.mjs restates check (or spn-devex restates check, once installed)

This is why a broken link is a worse defect here than in most repositories. A partner cannot follow it to the source, so the restatement has to stand on its own.

The domains it holds

This repository is a monorepo of plugins, so it divides by plugin.

A monorepo divides by the thing it holds many of, and what this one holds many of is Claude plugins for SaaS Plane. Each is a domain, with a section of its own in the concept and one folder of the same name in every What seat.

DomainShipsInstruments it carries
spn-devex the stack-agnostic plugin, loaded by every repository whatever world it declares all five kinds — plugins, hooks, skills, refs and agents
spn-apps the TypeScript stack plugin checks, tools, skills and refs, each true of that stack and nowhere else
spn-infra the estate plugin one guard, plus the skills and refs that change an estate

devex — spn-devex

The stack-agnostic plugin, and the one every repository loads. Its constructs are in 02-constructs/01-devex/, and read one folder at a time in the devex overview.

The risk in dividing by delivery is that somebody with a general question has to guess which plugin answers it. It does not arise, because a grammar shared by all three lives in spn-devex and the stack plugins restate none of it. The same hook grammar governs a check here and a check in spn-apps, so what a hook is has one answer in one place — spn-devex's hook set. A stack plugin's chapter says what its own checks decide, never what a check is.

The five instrument kinds are a shape, not a seat. Plugin, hook, skill, ref and agent are what an instrument can be, each defined once, in spn-devex. They are the vocabulary the three domains are written in rather than a division of the tree — which is why you find the hook set as a chapter under spn-devex and never as a folder of its own.

apps — spn-apps

The TypeScript domain plugin. It holds what only a stack can say: a check whose rule is true of one stack and nowhere else, a tool over that stack's own register, and the skills that can only be said in its own words. A skill that is stack-agnostic stays in spn-devex and reaches a concrete step through a ref here, rather than being copied. Its constructs are in 02-constructs/02-apps/, and read one folder at a time in the apps overview.

infra — spn-infra

The estate plugin. It holds what changes an estate: one shell script standing between an estate edit and the file it would write, the skills that change what an estate is, and the estate's own vocabulary restated for a reader who may never open the book. Its constructs are in 02-constructs/03-infra/, and read one folder at a time in the infra overview.

The world it declares

This repository declares GENERAL, which is a world with no stack in it.

A repository's manifest declares which world it belongs to — FOUNDATION, APPS, INFRA or GENERAL — and a public marketplace is the last of those. It ships no application, no package a service depends on, and no estate declaration; it holds one docs tree and no nodes at all, so the apps and infra commands refuse it by name.

A tool finds a docs tree by the docs/ folder on disk, never by what a manifest declares (Q107, 2026-09-20). So a tool you run here must tolerate the absence of nodes rather than refuse the repository — and if one refuses you, that is the tool's defect and not this repository's.

The same absence decides where the source lives. With no node in the repository there is no src/ at all: the source root is plugins/, and the capabilities seat mirrors it folder for folder, one document per source folder that earns one, each named for the folder it governs. Add a checker and write no mirror for it, and you have added a surface nobody documented — which is exactly what the coverage invariant is there to tell you.

One thing that absence does not excuse. The foundation book names a checker only where one of its rules cites that checker, and four checkers it does not name at all. Naming is not documenting: the rule belongs to the book, and the implementation belongs here.

Glossary

The words this page leans on. Each is meant in the narrow sense this repository gives it, and where the foundation book defines one, the book wins.

WordWhat it means here
the marketplacethis repository, and the public listing at its root that tells a runtime which plugins exist and where each one sits
a pluginone delivery unit — a manifest and a folder tree — holding any of the five instrument kinds. Three are shipped: spn-devex, spn-apps, spn-infra
an instrumentthe house word for anything this repository delivers to a session: a hook, a tool, a skill, a ref, a lens or an agent brief
a hookcode the runtime calls for you at a named moment of the loop. It returns a verdict rather than printing one, and only one of the four moments is allowed to refuse anything
a skilla stage's steps, in a folder with a description written to be matched against the work at hand rather than browsed by a person
a refa restatement of one or more chapters of the foundation book, carried here in full so a reader with no book checkout can still read it
the stampthe hash of the chapter a ref last saw. It is what turns a moved chapter into something reported rather than discovered later
a lensone reviewing viewpoint, naming the single thing it may block and everything it can only advise. A panel is convened by naming one
an agent briefa persona a session can convene, and the bound authority it carries once it runs — which for most of them excludes writing
the bookthe foundation repository, which states the rules this one delivers. It is private; this one is not, and that asymmetry is the reason restatement exists
