Nothing in this plugin changes a cloud.

The one boundary every folder in this plugin keeps: nothing here touches a cloud directly.

spn-infra is the plugin an estate repository loads, and this page reads it one folder at a time, around the one boundary every folder keeps. Read it before you add a rule about what an estate declaration may contain, or when you want to know what this plugin catches and what it leaves to the tool. It takes each folder in turn and sends you to the page that states it in full.

Overview

An estate declaration says what infrastructure should exist, and some things must never appear in one: a credential, an account identifier a tool finds for itself, a cloud's own string outside the entry allowed to hold it. spn-infra catches those at the moment they are written, and explains the estate's words to a reader who may never open the book.

This page is for a DevOps engineer or an architect working in an estate repository, and for anyone about to add a rule or a cloud to this plugin. It assumes you know what a plugin is; if you do not, the spn-devex overview comes first. After it you know where each estate rule is enforced, and what this plugin will never do for you.

The one thing to unlearn is that an estate plugin operates the estate. It does not. The gate refuses a bad write, the cards explain the vocabulary, and each skill names the command that does the work through the tool's own doors. A cloud is changed only by that tool, never by this plugin and never by a hand-run apply. This plugin ships no agents, and it has no chapter for them.

What you can decide after this page. Whether a rule you want is about the text of a declaration, and so belongs in the gate; whether it is the same on every cloud or belongs to one; and where its proof goes.

Plugin — spn-infra as a delivery unit

spn-infra is the folder that carries the estate standard into a session working on an estate: one manifest, one entry in the marketplace list, and the folders beneath it. Its version belongs to the set and moves with its two siblings whether or not anything here changed. Its description belongs to this plugin alone, and it is what a session matches against when it decides whether to load the plugin at all.

Hooks — one moment, every write

Every rule this plugin holds is about what a file contains, so the wiring is as narrow as the rules: the moment before a call writes or edits a file, and nothing else. That is the only moment that can still stop a write. An estate leak is cheap to catch while somebody writes it and expensive to find later, so this plugin claims that moment and no other.

Skills — the doors an estate is changed through

An estate is changed by editing what it declares itself to be, then letting a tool render and apply that declaration. The skills cover that walk: starting a new piece, changing what the estate is, reviewing and running a rendering before anybody approves it, verifying, and releasing a finished piece. They share one boundary, and each one states it: no skill changes a cloud. Each names the command that does.

Decide here: which request starts which walk, and which command each one hands the work to.

Scripts — the write-time gate and what runs it

The scripts tree is the catch. A dispatcher the wiring starts, a gate that works out which subjects have an opinion about the file, and a set of named rule bodies in lib/, each free of any cloud. Read the direction it fails in first: when the gate does not understand its input, it allows the call. A gate that refused everything it could not parse would deny far more than it knows about, and people would route around it.

Decide here: whether a new rule is a rule body the gate asks, and whether it holds on every cloud.

Refs — the estate's vocabulary, restated as cards

An estate is declared in a small vocabulary where every word is exact: which file marks a node, which layer owns which act, how a resource name is built, what a declaration must never contain. A card restates one of those subjects in full, for a reader who may never open the book. A card is a ref, so it carries a stamp and adds no rule. Every value in it is grammar, never a real one: no organization's environment, region or account appears.

Decide here: where to read an estate word before writing it, and what a card may never hold.

Read Refs →

Providers — one folder per cloud, scripts half only

Everything that differs between clouds sits in providers/, one folder per cloud, so admitting the next cloud is adding a folder. Here each folder holds a scripts half and no skills half. A skills half is earned when the instance changes what an author writes, and a cloud does not: a declaration is provider-neutral, and every rendering is written against OpenTofu whichever cloud it reaches. So the rule is the domain's and the parsing is the provider's.

Decide here: what a new cloud must bring, and why it brings no skills.

Read Providers →

Tests — the tier, the mirror, and a runner that walks

A gate nobody proves is a gate nobody can trust to be narrow. The rules here are patterns over text somebody is about to write, and a pattern one character too wide refuses correct files until somebody turns the whole gate off. So each rule is proven against what it must refuse and against what it must let through. The tier comes first and the mirror second, so moving a source file moves its proof with it.
