Only one folder in this plugin may name a language.

The extra rules only a TypeScript repository needs, on top of what every repository already has.

spn-apps is the plugin an apps repository loads, and this page reads it one folder at a time, with the stack kept inside its own provider. Read it before you add a rule that can only be written for one language, or when you want to know what is different here from the plugin every repository loads. It says only what differs in this domain, and sends you to the page that states each part in full.

Overview

An apps repository is held to rules about what its contracts, services and tests contain, and some of those rules can only be written for one language. spn-apps carries them. Each folder here is the same kind of instrument spn-devex defines.

This page is for a backend or web developer working in an apps repository, and for anyone about to add a rule or a stack to this plugin. It assumes you know what a plugin is; if you do not, the spn-devex overview comes first. After it you know which folder a change to this plugin belongs in, and why most of the plugin never names a language.

The one thing to unlearn is that a stack plugin is written in its stack everywhere. Most of this plugin is stack-agnostic. The skills and the gate read which stack a node declares in its own sprepo.json, then load the stack's part from providers/. So adding a second stack is adding a folder, not editing a gate. This plugin ships no agents, and it has no chapter for them.

What you can decide after this page. Whether a rule you want to add is true of every stack or of one; which folder it then belongs in; and where its proof goes.

The Plugin — what spn-apps is, and when a session loads it

Everything this domain ships sits in one folder, and that folder is what an install copies. Its identity is its own: the name and the description in its manifest say what it carries, and the description is what a session matches against when it decides whether to load the plugin at all. Its version is not its own: every plugin in this marketplace carries the same number, and a release moves all of them together.

Decide here: whether the description says enough for a session in an apps repository to load this plugin.

Hooks — one moment, because every rule here is about a file

This plugin wires one moment: the call about to write or edit a file. Every rule it holds is about what a file contains, so reading a file, running a command or ending a turn could never break one of them, and a hook there would cost a start-up and answer nothing. The one entry names a single process, which asks every rule that applies and returns one verdict.

Decide here: whether a new rule is about a file's text, and so runs at the moment of writing.

Read Hooks →

Skills — the commands an apps repository answers to

A skill belongs here when its work is work on an apps node: starting a project, building a capability, reviewing, running the suites, proving a package and releasing. A skill here names no stack. It states the order of the work and reads the steps for each language from the provider the node declares. Planning is not a skill of this domain: it is folded into the stack-agnostic planning skill in spn-devex, which loads the stack's planning step from this plugin's provider.

Scripts — the code this plugin runs

The folder divides by what calls each file. The wiring starts one process, which asks one gate; the gate reads the declared stack and resolves into a provider's checks without naming a language itself. Tools are run by a person or the agent by their own path, and read this stack's registers. A tool writes only what a run found, because the rest of a behaviour row is somebody's decision and must not be replaced by a guess.

Decide here: whether a new piece of code is a check the gate asks, or a tool somebody runs.

Refs — the book, restated inside the plugin

A partner holding this plugin has no copy of the foundation book beside it, so a rule the plugin needs is written out inside it. The folder mirrors the book's own domains. A ref states and never executes: it says what is true of an apps node, and anything a skill performs lives elsewhere. A ref adds nothing to the book, and each one says which version of the book it was read at, so a copy that has fallen behind is reported rather than believed.

Decide here: whether a fact a skill needs is a restatement of the book, and where in the mirror it goes.

Providers — where the stack is allowed to be named

Nothing else in this plugin may name a language. Everything that varies with the language a node is written in sits in one folder per stack under providers/. Here the provider always carries both halves: the checks the gate dispatches into, and the steps a skill loads. The reason is that in this domain the instance is the stack itself, so writing a contract, a service or an entry is a different procedure in each language.

Decide here: what a second stack must bring, and which of its rules belong to the provider rather than the gate.

Tests — the stack's own folders, without the stack's framework

This plugin holds other people's repositories to rules, so it owes proof of its own. Its suites follow the folder convention this domain asks of every node: at the plugin root, divided by tier, never beside the source. What is not followed is the choice of runner. The suites drive real hook processes through standard input and read what they write back, so a test framework would wrap one harness in another and add nothing.
