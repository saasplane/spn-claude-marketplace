A plugin is a folder of instruments, and this one defines what each instrument is.

The plugin every repository loads, read one folder at a time.

spn-devex is the plugin every SaaS Plane repository loads, and this page reads it one folder at a time, in the order the folders depend on each other. Read it before you decide where a new rule should run, or when you want to see what a plugin can hold at all. It takes each folder in turn, says what it is for and what you would decide there, and sends you to the page that states it in full.

Overview

A rule in the foundation book does nothing until something applies it while you work. spn-devex is where that happens for every repository, whatever world it declares. It is also the widest of the three plugins, so it is the place to learn what a plugin can hold at all.

This page is for anyone about to change a plugin in this repository, or to read one: an architect deciding where a new rule should run, or a backend developer about to write a check. It assumes no earlier reading. After it you know which folder a piece of plugin code belongs in, what that folder promises, and which construct page to open next.

The one thing to unlearn is that a plugin makes rules. None of them does. Every rule is stated once, in a chapter of the foundation book, and a plugin carries instruments that read that rule and apply it at the moment somebody works. So each folder below is one kind of instrument, and each is defined once, here in spn-devex. The other two plugins use the same folder names and add what only their own domain can say. That is why a general question, such as what is a hook?, always has its answer in this domain.

What you can decide after this page. Which folder a new piece of plugin code belongs in; whether a rule you want to enforce should run at the moment a file is written, or only when somebody asks for a sweep; and what has to happen before an edit to a plugin is the code a session actually runs.

The Plugin — the folder a session installs

The plugin is the unit that carries a rule from this repository into a running session: one folder, one small manifest in .claude-plugin/plugin.json, and one entry in the marketplace list this repository keeps by hand. A session never reads this checkout. It reads an installed copy, found by the plugin's name and the version its manifest carries, so an edit here is not yet a change in behaviour. The version names what is published, and it moves after a release, never before.

Hooks — code the session runs for you

A hook is code the runtime calls at a moment it chooses, so a rule is asked again on every call instead of being remembered from a document. hooks/hooks.json declares the wiring: which moments of a session a plugin claims, narrowed to the calls it could have an opinion about. The moment decides the authority. Only the moment before a call runs can refuse it; every later moment can only advise. A hook returns its decision rather than printing it, and it always exits zero, so one crash never takes the other gates down.

Decide here: which moment a new rule should run at, and whether it may refuse or only advise.

Refs — a chapter, restated and stamped

A reader may hold the plugins and never hold the book, so a ref restates a chapter inside the plugin. It is a copy made on purpose, and it carries a stamp: the hash of the exact text it last read. A run that compares the stamp with the book can then report that a chapter has moved since it was copied, instead of the copy quietly going out of date. A ref adds no rule. Where a ref and its chapter disagree, the chapter wins and the ref is rewritten.

Decide here: whether a rule a plugin needs should be restated in it, and how its copy is kept current.

Agents — a second reader, convened mid-turn

The context that wrote a change already agrees with its own reasons, so a review needs a different reader. An agent brief is that reader: a persona with its own name that a session convenes mid-turn, holding only the authority its own file grants it. A reviewing brief carries no viewpoint of its own. It is handed a lens when it is convened, one file per engineering function, and the lens states what that review may refuse and what it may only advise. The book calls this viewpoint a lens.

Decide here: which viewpoint a piece of work should be reviewed through, and what that reviewer may block.

Skills — a named piece of work

Loading every rule into every turn would bury the one rule the turn needed. A skill narrows the loading: a folder with a name, a description, and the steps for one kind of work, read only once the work at hand matches the description. The description is matched against what you type, not read by a person browsing a list, so it states the kind of request it answers in the words a developer uses. A skill carries steps and never a rule of its own, because a rule that lives only in a skill is a rule nothing can check.

Decide here: what a request should be called so it runs the same steps every time.

Scripts — the code a plugin runs

Everything a plugin can execute sits under scripts/, divided by what calls it: events/ for the process a hook moment starts, checks/ for the questions it composes, tools/ for what a person or the agent runs by its own path, and lib/ for what both read. A rule answered one way while a file is written and another way in a sweep would be two rules, so the code that decides lives once and both callers import it. Every script names the chapter it applies in its own header.

Decide here: whether a rule should be a check wired to a moment, a tool run on request, or both sharing one library.

Providers — where an instance may be named

A plugin that names its stack or its cloud in a gate is a plugin the next stack cannot join. A provider is one folder per instance, under providers/, holding everything that varies with it: a scripts half that a gate dispatches into, and a skills half only where the instance changes how the work is written. Every gate reads the instance from the nearest sprepo.json. spn-devex defines this construct and ships no providers/ folder itself, because nothing it does varies by instance.

Decide here: whether a new stack or cloud needs a folder of its own, and which halves it contributes.

Read Providers →

Tests — how a plugin proves itself

A plugin is code, so it owes proof, and the proof sits where a reader can work out its path without searching. Under tests/ the tier comes first and the mirror second: unit/ says what kind of proof a suite is, and the path under it repeats the path of the source file it proves. The runner finds every suite by walking the folder rather than reading a list, and no suite counts its own depth, so moving a file does not break the suites around it.

Decide here: where the proof for a new script goes, and how to run it.
