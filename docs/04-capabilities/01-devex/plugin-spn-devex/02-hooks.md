# Hooks in spn-devex

`For: Backend developer · Architect` · `Status: ✅ DONE` · `Realizes: Hooks`

`spn-devex` is the only plugin that wires more than one moment: all five, one script each, none of them reached any other way. It also realizes the parts every other hook in the marketplace reuses — the payload and verdict shapes, the dispatcher that composes many checks into one answer, and the timing that says what all of it cost. Two decisions shape the rest. **The moment decides the authority**: a call about to run is the only place a call can still be stopped, so the other four speak and nothing more. And **a check returns its verdict instead of printing one**: the earlier scripts each printed JSON and exited, and the dispatcher parsed what it could read — which is how one check fired one hundred and forty-seven times and changed nothing.

| A call about to run | `packages/plugin-spn-devex/src/scripts/events/pretooluse.ts` | `PreToolUse`, matching `Read`, `Write`, `Edit`, `Bash`, `Grep`, `Glob`, `NotebookRead` and `Artifact`, and the dispatcher behind it |
| A shell command that finished | `packages/plugin-spn-devex/src/scripts/events/closed.ts` | `PostToolUse` and `PostToolUseFailure`, matching `Bash` |

## Special handling

### A verdict is a return value

**Why** — *a refusal that travels through stdout can be lost on the way*. Redirecting output, swapping arguments and parsing the last line gives a refusal several places to disappear, and it disappeared in all of them.
**What** — each check is a function returning `{ deny?, note? } | null`. The dispatcher calls it and reads the object. A file can still be run on its own, and then `emit` prints the same JSON to the same stream.
**How** — `emit` sets `permissionDecision` and `permissionDecisionReason` for a refusal and `additionalContext` for a note, because a message put only in the developer's pane is invisible to the agent. `packages/plugin-spn-devex/src/scripts/lib/payload.ts`.

### Exit zero, always, and a throwing check is skipped

**Why** — *a hook that crashes takes every other gate in the chain with it*. One broken rule must never remove the rules beside it.
**What** — a refusal is the documented decision on stdout and never a non-zero exit. Inside the chain, a check that throws is caught and passed over; the rest still run.
**How** — the dispatch loop wraps each call, and the top level wraps the whole dispatch before emitting. `packages/plugin-spn-devex/src/scripts/events/pretooluse.ts`, the `dispatch` function and the lines under it.

### One process, cheapest check first

**Why** — *five hooks matched one edit and each paid an interpreter start-up before reading a byte*. Measured on 8 September 2026, the chain cost 117.7 ms per edit and 60 ms of that was five programs starting.
**What** — `hooks.json` declares one `PreToolUse` entry. The dispatcher imports every check, and each declares what it `applies` to and which fields it `needs`, so a call that cannot interest a check never reaches it.
**How** — the order is a path test, then a file read, then a workspace walk, and the tree-reading check is last. `packages/plugin-spn-devex/src/scripts/events/pretooluse.ts`, the `CHECKS` list.

### A hook runs a committed bundle, not its source

**Why** — *a fresh process pays for start-up on every call, and type-stripping a TypeScript source is the largest piece of it* — the foundation's `04-plugins/02-shape.md` § *Why a hook runs a bundle* states the general case and the measurements it rests on.
**What** — `hooks.json` names `dist/events/*.mjs`, never `scripts/events/*.ts`. Measured on this machine, 2026-09-28: `PreToolUse` fell from 63 ms to 26 ms.
**How** — `pnpm build:plugins` at the marketplace root rebuilds every plugin once; `pnpm build:plugins:watch` rebuilds on every source change while editing a hook; `spn-devex plugin build` runs the same script from inside any plugin checkout. An edit to a hook's source is not live until the next rebuild — `tests/unit/t-dist-current.mjs` refuses a bundle older than its sources, so an unrebuilt edit fails the suite by name rather than running silently stale. The hash of a bundle's sources follows each import inside the shared support folder. So an edit to a shared file that only another shared file imports still marks every bundle that reaches it as stale. `packages/plugin-spn-devex/src/hooks/hooks.json`, `packages/plugin-spn-devex/src/scripts/commands/plugin/build.ts`, `scripts/lib/source-hash.mjs`.

### A publish is reminded, and refused only where the page links its styles from outside

**Why** — *the agent publishes no page unless the developer asks* (RD.DEVEX.WORKSPACE.117), and the habit came from the publishing tool's own default, which a rule in a reference file loses to at the moment of the call. The hook cannot know whether the developer asked.
**What** — `hooks.json` routes the `Artifact` tool through `PreToolUse`. A call that publishes a page — no action, or `publish`, and not an asset upload to a page already published — gets one note stating the rule and the full path to hand over instead, and the call goes ahead. One thing is refused, because the check can read it from the file: a page that loads a stylesheet or a script from an address a published page may not load. The refusal names `spn-devex docs sds bundle <page>` and the copy to publish, `<name>.bundled.html` (RD.DEVEX.WORKSPACE.215). A file that cannot be read is reminded and not refused.
**How** — `dispatch` returns the note, or the refusal, before the check list. `packages/plugin-spn-devex/src/scripts/checks/publish.ts`, proven in `packages/plugin-spn-devex/tests/unit/scripts/checks/t-publish.mjs`.

### A page links a version that was cut

**Why** — *a stored page links one version by its address* (RD.DEVEX.WORKSPACE.214), and a page that links a version nobody cut shows no styling at all.
**What** — a write of a page that links the shared stylesheet is refused where its version is not in `versions.json`, and the message names the version and the versions that exist. A page that links no shared stylesheet gets one RULE line, and no finding about a card or a status, because no class of it is read.
**How** — the check reads `versions.json` in the plugin's `styles/` folder, which sits beside `dist/` in an installed plugin. `packages/plugin-spn-devex/src/scripts/checks/doc-check.ts`.

### The first refusal is the answer; advice adds up

**Why** — *a refusal ends the call, so anything after it is noise*, while two pieces of advice are worth more than one.
**What** — the loop returns on the first `deny` and joins every `note` into one message.
**How** — the generated-file guard runs before the list, because it refuses from the path alone and needs nothing else read. Same file, `generatedRefusal`.

### A source edit waits while a test run is going

**Why** — *no source or test file changes while a test run for that repository is in flight* (the book's RD.DEVEX.WORKSPACE.207). In workstream 008 an edit made during a contract run cost a full rerun.
**What** — a write under a repository's `src` or `tests` folder is refused while a test command for that repository has a start file. The refusal names the run and how long ago it started. A write to a document, to another folder, or to another repository gets no verdict. The guard knows a run only by its start file. So it sees no run while recording is off, and none that was started in the background. It sees none started by a program the filter does not name, such as `pnpm test`.
**How** — the check reads each file under `.spndevex/.debug/telemetry/pending/` by path, as the hook after the call does. A test command is `spnutils apps test`, `spnutils infra test`, `nx test`, or `nx run-many` with `test` as its target. The repository is the first folder below the workspace root, for the run and for the write. A Bash command is judged by the paths it writes. A start file older than 600,000 ms is not read as a run, because no foreground Bash call outlives the harness's longest timeout. Without that bound, a start file that no call closed would refuse every edit in its repository for a day. `packages/plugin-spn-devex/src/scripts/checks/test-run.ts`, an entry in the `CHECKS` list of `packages/plugin-spn-devex/src/scripts/events/pretooluse.ts`, proven in `packages/plugin-spn-devex/tests/unit/scripts/checks/t-test-run.mjs`.

### A block `spnutils` writes is never edited by hand

**Why** — *the text between the `spnutils:agent` markers is written by a command*, so a hand edit there is lost at the next sync. The generated-file guard refuses whole files, and this block sits in files that also hold a person's own text.
**What** — an `Edit` whose `old_string` sits between the markers is refused. A `Write` is refused where its text between the markers differs from the file on disk. The refusal names `spnutils workspace agent-sync` and `spnutils repo agent-sync`, the commands that write the block. An edit below the end marker passes, and so does a `Write` that keeps the block's bytes. A Bash call that runs either command is not judged, because the command writes the block itself.
**How** — a marker counts only where it is a whole line: `<!-- spnutils:agent:begin -->` and `<!-- spnutils:agent:end -->`. A file that quotes a marker inside a line holds no block, so source code and plans that name the markers are left alone. A plugin imports nothing from `spnutils`, so the marker lines are written here a second time. The header of the file names their source, `managed-keys.ts` in `spn-support-ts`. `ToolInput` carries `old_string` and `replace_all` for this guard. `packages/plugin-spn-devex/src/scripts/events/pretooluse.ts`, beside `generatedRefusal`, and `packages/plugin-spn-devex/src/scripts/lib/payload.ts`, proven in `packages/plugin-spn-devex/tests/unit/scripts/events/t-pretooluse.mjs`.

### An arc's tables are judged whole when the arc is written

**Why** — *a step row with a wrong cell count is read one cell to the left*, and nothing said so until the close. In workstream 008 the close found 41 such rows at once. A preview named without a link showed on the page as plain text, and nothing reported that either.
**What** — on a write of an arc file, a step row whose cell count differs from its header's is reported with its number and both counts. A row of the arc's Previews table whose File cell holds no link is reported too, and the note shows the link form. A pipe written with a backslash before it stays inside its cell, so a row that holds one is not reported. A section that reads `None.`, an arc with no Previews section, and an arc of workstream 008 are left alone.
**How** — an `Edit` carries only its replacement, so the edit is applied to the file on disk and the whole arc is judged. Both findings are notes, and the write goes ahead. The close gate's reader splits a row the same way, so the gate and this check read one row as the same cells. `docs cycles` prints an unlinked preview row as a `!` line. `arcSteps` and the Previews reading beside it in `packages/plugin-spn-devex/src/scripts/checks/doc-check.ts`, `previewsOf` in `packages/plugin-spn-devex/src/scripts/commands/docs/cycles.ts`, and `mdTables` in `packages/plugin-spn-devex/src/scripts/checks/split-plan.ts`, proven in `packages/plugin-spn-devex/tests/unit/scripts/checks/t-doc-check.mjs` and `packages/plugin-spn-devex/tests/unit/scripts/commands/docs/t-cycles.mjs`.

### A card in an approach page's Open is asked for its Views part

**Why** — *a card showed the option the agent preferred, and nothing on it said whether any other role had read the choice* (RD.DEVEX.WORKSPACE.242).
**What** — on a write of an approach page, a card in the `Open` section with no *Views* part is reported as a RULE finding, beside the findings for a card with no options table or no recommendation. A card in `Deferred` is not asked for it, and no check reads the part in a reply.
**How** — the check reads presence only: an element of class `sds-key` whose text is `Views`, inside the card. The word in the card's title or prose is not the part, and what the part says is never judged. The finding is a note, and the write goes ahead. `openCards` in `packages/plugin-spn-devex/src/scripts/checks/doc-check.ts`, proven in `packages/plugin-spn-devex/tests/unit/scripts/checks/t-doc-check.mjs`.

### The session's first screen is read from the ground

**Why** — *the workspace is discovered, never declared*. A file naming the members in prose is wrong the first time somebody clones another repository, and a repository that is absent is not missing.
**What** — nothing in the opening screen is typed. The script walks the root, reads each `sprepo.json` for the world and the stack claim, checks the wiring that claim implies, and lists every workstream in all three states. Where no manifest exists anywhere, it asks instead of reading and points at the `bootstrap` skill.
**How** — the first reply opens with the welcome, whatever the prompt, then **one status line** — `7 repos · 1 workstream open (008) · 3 other windows open here` — that drops any part reading zero and adds a clause, never a second line, for an unwired repository, a stale plugin, or a rung below an ordinary session. The tables of repositories and workstreams, and the one open question, are held back for when you ask: a reply opening on a table shows numbers before anybody asked for them. Every read is wrapped and the exit code is always zero, because this output is the session's first screen and a crash here is a window that opens on a stack trace. `packages/plugin-spn-devex/src/scripts/events/orientation.ts`.

### The short rules are printed once, at session start

**Why** — *the agent follows only the rules it has read* (the book's RD.DEVEX.AGENT.089). A reference is read when a skill names it, and a reply in the middle of an arc calls no skill. So the rules on views and on the shape of a reply did not reach that reply.
**What** — the session-start script adds a block to what the agent reads, after the ground and its note: the heading *The short rules*, then ten list lines. They cover views in a discussion about a shape, the three signs and what each number of signs brings, a view in its own voice, a reply that reads as one person talking to another, a decision that sets a shape, structure before content, the two cases of **Needs you**, and who manages arcs and workstreams. The last line says that no script judges a prompt. The developer's pane does not show the block. Day zero prints it too.
**How** — each line ends with `→`, the path of its reference from the plugin's root, `§`, and the heading that holds the rule whole. The lines are typed in the script, as the welcome is, because the plugin runs where the book is not present. Nothing reads the prompt. `SHORT_RULES` and `shortRules` in `packages/plugin-spn-devex/src/scripts/events/orientation.ts`, proven in `packages/plugin-spn-devex/tests/unit/scripts/events/t-orientation.mjs`, which opens every file a line names and looks for every heading.

### A session is named for the workstream and the arc it works on

**Why** — *a window is found in the session list by its name* (the book's RD.DEVEX.WORKSPACE.222). A name that says nothing about the work makes the developer open each window to find one. Claude Code reads a session's name from a hook on two events, `SessionStart` and `UserPromptSubmit`, and only the prompt says which work the window takes.
**What** — `hooks.json` runs one script on `UserPromptSubmit`, with no matcher. A prompt that names exactly one workstream folder that exists in `open/`, `backlog/` or `closed/` names the session after that folder, such as `020-agent-workstream-improvements`. That form is given only while nothing is recorded for the session. A prompt that holds a handover block names the session from its `continue:` line: the workstream's number, the arc's number and the subject of the arc's file name, such as `020-N011 artifacts-by-domain`. A handover whose arc has no file in `arcs/` gives the folder's name, and so does the reload form of `continue:`. A prompt that names no workstream gets no answer, and neither does one that names two with no handover. The script answers only where the name differs from the one it recorded last. Claude Code keeps a typed name and a given name in one record, so an answer on every prompt would write over the name the developer typed. A later prompt that names another workstream changes nothing, so a session keeps the arc it started on.
**How** — the answer is `{"hookSpecificOutput":{"hookEventName":"UserPromptSubmit","sessionTitle":"<name>"}}` on stdout. The record is one file for each session, `.spndevex/.debug/names/<session id>.json`, and it holds the name and its form. It is written before the answer is printed, and a name that cannot be recorded is not given. A payload with no session id gets no record and no name. The first workstream the `continue:` line names is the one the window works on. The arc is read only from the text before a second workstream, so the arc that waits in the reload form is not taken. The handover's lines and the patterns for a workstream and an arc are the ones the Stop hook reads, imported from `stop.ts`. Every error ends in exit 0 with nothing printed, and the script starts no other program. A run is timed as `prompt › name` and `events › prompt`. `sessionName` and `nameToGive` in `packages/plugin-spn-devex/src/scripts/events/prompt.ts`, proven in `packages/plugin-spn-devex/tests/unit/scripts/events/t-prompt.mjs`.

### A window's workstreams are bound by the path it wrote, and every hook speaks only of them

**Why** — *a window on one workstream was asked for the cards of another* (the book's RD.DEVEX.WORKSPACE.236, from RD.DEVEX.WORKSPACE.197 and RD.DEVEX.WORKSPACE.198). The Stop hook took any workstream whose folder name appeared in the text of a write, a log line included, and kept it for ever, and the note before a tool runs read every open workstream with no window at all.
**What** — a window **owns** the workstream its first prompt names and every workstream a handover names, or, when nothing names one, the first folder a write of the window went inside; any other folder it writes inside it only **visits**, and a visit never becomes ownership. For a visited workstream only the single-file standard on the file written and the notes rule for an arc the window itself changed apply, never its cards, `needs-you`, handover or rows. A read, a mention, a brief and a prompt that names two workstreams tie nothing. Every message names the workstream and the tie. A window that owns none hears nothing about a card, a page, an arc or a row, and a workstream that leaves `open/` drops out. A call a child makes binds its window, because it carries the window's session id, and the child itself hears no card or page note. A note before a tool runs is said once for one finding and again only when the finding changes. The session-start listing, `release-go`, the close gate and the checks of one written file stay across the workspace, because each names a version, a folder or a file. `corpus` does not: it runs the docs commands only over the repositories the window has written under by path (the note's `repos`), marks a finding in a file that is changed and not committed as work in progress, and says of a replayed verdict only what its key compared. A child's writes count for the window because a child carries its window's session id; that is inferred and not yet proved, and where it is false the window hears less, which is the safe side.
**How** — `lib/window.ts` keeps one file for each session, `.spndevex/.debug/windows/<session id>.json`, removed after fourteen days: the workstreams bound and how, the time each arc was last written, and the last finding of each note told. `PreToolUse` records the paths a call writes (a file path, a shell write, a `mkdir`, the place a move lands) before any check reads them. `UserPromptSubmit` records the prompt and handover bindings. Both write by a rename and never fail a call. `windowSet` and `windowWorkstreams` are the one reader, and they return the empty set for a window with no binding or no session id. `ownWorkstreams` in `split-plan.ts` gives the documents-first gate its pages, and `confirmed` looks for a go in the window's workstreams, and in every open one only where the window has none. A write made by an interpreter's own script, such as `python3` run from a heredoc, names no path the hook can read, so it binds nothing; the next `Edit`, `Write`, shell write or prompt does. `packages/plugin-spn-devex/src/scripts/lib/window.ts`, proven in `packages/plugin-spn-devex/tests/unit/scripts/lib/t-window.mjs`.

### The close is congratulated after it lands, not before

**Why** — *the close gate runs before the move and speaks only to refuse*. Congratulating from there would congratulate something that has not happened and might still fail.
**What** — `PostToolUse` on `Bash` reads the command's own `mv`, and when a workstream folder has actually moved into `closed/` it says what landed, counted from that page's split plan.
**How** — the subject is taken from the source of the move, because `mv <subject> closed/` is how a close is typed and the destination is then only a structural name. It reads the same parser the close gate refused with, so both count the same table. `packages/plugin-spn-devex/src/scripts/events/closed.ts`.

### A turn that ends warns and never refuses

**Why** — *the turn is already written*, and a refusal at that point would only lose it. A warning makes the agent reply again, so a check speaks once in a turn and only about the session's own work (RD.DEVEX.WORKSPACE.197 · RD.DEVEX.WORKSPACE.198).
**What** — warnings for a reply that puts a decision with the card's shape incomplete, a reply that owes **Needs you** at its top and does not open with it — a reply that raises a card holds it there in full once, and a reply that waits names every card open from an earlier reply in one line, while a progress reply owes nothing (RD.DEVEX.WORKSPACE.189) — an answer logged in an arc whose notes (spec, plan, previews, samples) did not move in the same turn, a proposed arc carrying a review point to a later step of itself (RD.DEVEX.WORKSPACE.193), an arc *this session* wrote to that still has runnable rows and no card open, an arc marked `HELD` that names no live card, a reply that passes work on and leaves an open card unnamed or carries a handover block that lacks a label, and the corpus questions a whole-tree read still owes. A page left stale, an arc that landed with a row undecided, and a handover whose values start in different columns each have a section below.
**How** — a check that spoke at the session's last Stop is skipped while `stop_hook_active` is true, because the reply is its answer; the baseline keeps what spoke earlier in the turn beside what spoke now. The cards, the hold check, the four arc-to-page checks, `notes`, `carried` and `runnable` read the workstreams this window works on, taken from the window's note (the section above), and no others; a window with none is read for none. The baseline keeps no list of workstreams, and an old baseline that holds one is not read. Every message names its workstream by folder name, and a page or an arc by its path from the workspace. The baseline also keeps the cards open at the session's last Stop, so a card open now and not then is the one this turn raised. The Stop event does not say whether the agent now waits, so `workRuns` reads the rows of this window's arcs: while one is marked `in progress`, in an arc whose status is not terminal, the reply is a progress reply and no line is owed for an older card; a row whose order is out with an agent counts as work that runs. A card this turn raised is asked for in full either way. A line that names a card open before this turn is set aside before the reply is read for a choice by letter, so the one line of an older card, with its recommended letter, never draws `reply-shape`. The baseline also keeps each open arc's log entries (hashed), its notes' size and time, and its status, so a new log entry recording an answer is judged against notes that did or did not move. An arc's notes are `notes/N<nnn>/spec.md`, `plan.md`, and every file under `previews/` and `samples/` in that folder; the warning names the spec and the plan by file and each of the two folders once. The arc number is read as the file name writes it, with one, two or three digits. `runnable` reads a baseline kept per session, under `.spndevex/.debug/stop/sessions/`, comparing each open arc's step-row hash against what this session last saw and reading the window's note for which arcs it wrote since its last Stop — so an arc another window is executing never fires here. A status of `PROPOSED`, `DECIDED` or `HELD` is never runnable, whoever touched it, and a row already marked `in progress <date> <time> <offset>` is named with its age rather than counted as unfinished, because somebody may still be on it. Such a row is not reported at all while an order for it is out: an order file under the arc's `notes/N<nnn>/orders/` that has no report beside it. A background agent is carrying the row out, and the window that sent the order has nothing to run. `[handover]` reads a pass-on only where a verb sends the work to another session, or the next session is said to start somewhere, and never where a session is merely named. It strips fenced blocks, code spans, block quotes and quoted text before it looks for that phrase, so a reply quoting the check's own words, or a `diff` block previewing a change, is never mistaken for one. `packages/plugin-spn-devex/src/scripts/events/stop.ts`.

### While a row is in progress, only a finding about the reply sends the agent back

**Why** — *every finding made the agent reply again, and the developer saw that reply* (the book's RD.DEVEX.WORKSPACE.244). While an arc ran, a finding about a page or a docs tree produced a second progress reply that said nothing new.
**What** — while `workRuns` is true, four checks still exit 2: `needs-you`, `reply-shape`, `handover` and `welcome`. Each is about the reply the developer is reading. Every other finding is held, and the hook exits 0 when nothing else spoke. At the first turn end where no row is in progress, each finding that is still true is said whole. A finding that the agent fixed in between is not said.
**How** — a held finding is not stored as text. A Stop hook can keep one thing between turns, the session's baseline file, and it already compares against it. So a turn end that holds a finding writes the baseline with its marks where they were: the time, each arc's step-row hash, each arc's log, notes and status, and the pages already named for their own copy of the styles. An arc that is new since then takes its marks from now. The next turn end compares against the same marks, and the checks that read the files as they are find their finding again by themselves. The cards open at the turn end and the checks that spoke are written as always. `splitFindings` and the hook's last lines in `packages/plugin-spn-devex/src/scripts/events/stop.ts`, proven in `packages/plugin-spn-devex/tests/unit/scripts/events/t-stop.mjs`.

### A handover block is asked for once

**Why** — *a handover block is written once, in the reply that passes the work on* (the book's RD.DEVEX.WORKSPACE.189 and RD.DEVEX.WORKSPACE.198). The check had no memory of a block. Any later reply that named the next window was told to write the block again, and so was the reply that answered another finding on the handover reply. A pass-on over an open card was told to put the card in full.
**What** — when a reply holds a whole block, the baseline keeps a hash of the step rows of this window's arcs. While those rows have not moved, a pass-on with no block draws no finding. Once they move, the old block no longer says where to start, and a block is owed again. A block printed a second time is still read. A pass-on while a card is open is asked to name each open card in one line, on the block's `open:` line, and never to put it in full.
**How** — `givesHandover` reads a filled-in block with all nine labels. `stepsMark` hashes the step-row hashes of the arcs in the window's workstreams. `checkHandover` takes the answer as its fourth argument. A reply that puts a whole card is still left alone, because it asks a question and hands nothing over. `packages/plugin-spn-devex/src/scripts/events/stop.ts`, proven in `packages/plugin-spn-devex/tests/unit/scripts/events/t-stop.mjs`.

### A page left stale is named before the turn ends

**Why** — *the parts of a page that the arcs decide are produced, never typed* (the book's RD.DEVEX.WORKSPACE.204). A page read `PLANNING` after arcs had landed, and its table showed arcs as proposed while they ran. The write-time check sees a page only when the whole page is written. So an arc that moves leaves the page stale, and nothing says so.
**What** — when the session's own tool calls wrote an arc this turn, the page of that arc's workstream is compared with its arcs. The comparison covers the Cycles table, the header's status and the heading of `Open`. Where any of them differs, one warning names the workstream and the command that writes all of them, `spn-devex docs cycles write <workstream>`. A turn that wrote no arc gets no warning, and neither does a workstream another session wrote.
**How** — the check reads `touched`, the arcs this window wrote since its last Stop (from the window's note), so a first Stop with no baseline compares nothing. For each workstream it calls `cyclesRule` and the header rule that `doc-check` applies when a whole page is written. The header's status follows the arcs: `PLANNING` while no arc is past `DECIDED`, `IMPLEMENTING` once an arc runs or has landed, and `DONE` when the workstream closes. `packages/plugin-spn-devex/src/scripts/events/stop.ts`, beside `checkArcToPage`, proven in `packages/plugin-spn-devex/tests/unit/scripts/events/t-stop.mjs`.

### An arc that lands is given the close gate's report

**Why** — *the close refuses a row nobody decided*, and it said so only at the close, when every arc of the workstream is read at once. The moment an arc reaches `LANDED` is the moment its rows are easiest to account for.
**What** — an arc this session wrote is read when it reads `LANDED` now and read another word at the last Stop. Its rows are read as the close gate reads them, and a row that reads empty or pending is listed in one warning. An arc whose rows are all landed, carried or deferred gets none. An arc that already read `LANDED` at the last Stop is not read again.
**How** — the baseline keeps each arc's status, so the change is known without a second file. The report's tally is a function that returns lines, shared by the Stop hook and by `split-plan.ts` run by hand. A tick with no date and no landed word reads as pending in both readers, `stateOf` and the Stop hook's `isDone`. `packages/plugin-spn-devex/src/scripts/events/stop.ts` and `packages/plugin-spn-devex/src/scripts/checks/split-plan.ts`, proven in `packages/plugin-spn-devex/tests/unit/scripts/events/t-stop.mjs` and `packages/plugin-spn-devex/tests/unit/scripts/checks/t-split-plan.mjs`.

### The handover's labels are read as one column

**Why** — *the labels form one column, so a missing line is visible* (the book's workstream chapter, § Stopping in the middle is a handover). A block with every label present passed whatever column its values started in, and the next window read a block it could not scan.
**What** — once every label is present, each value must start in the column that `do not touch:` sets. A block whose values start in different columns gets one `[handover]` warning that names the column. A continuation line is not read as a label, so a wrapped value passes.
**How** — the labels are `continue:`, `model:`, `read first:`, `pins:`, `state:`, `live now:`, `done when:`, `do not touch:` and `open:`. The longest is `do not touch:` and one space follows it, so a value starts at column 14, counted from 0. `checkHandover` in `packages/plugin-spn-devex/src/scripts/events/stop.ts`, proven in `packages/plugin-spn-devex/tests/unit/scripts/events/t-stop.mjs`.

### Measuring is free; writing is the cost

**Why** — *telemetry must not make the gate slower*, and a gate that fails because timing failed is worse than a number nobody recorded.
**What** — every run is timed, and so is each Bash command the agent runs through a program the filter names. Every line has one shape — the program or plugin, up to three levels below it, the arguments, the time, the exit code, the repository and a UTC time — and names the workstream, arc, order and agent the call belongs to, so a later reading can join a cost to the work that paid it without guessing from a path. Whether any of it reaches disk is a switch the developer sets, and every path swallows its own errors.
**How** — `begin` touches no filesystem; the switch is read at the moment of writing, under a fixed size cap; `tagsOf` matches every string in a call's input against a workstream path and keeps the most specific match — an order over an arc over a bare workstream — reading the hook's own `agent_id` for which agent made the call. **The tags carry forward** (RD.DEVEX.WORKSPACE.185): per session and agent, the last tagged call's tags sit in `telemetry/tags.json`, written only while the switch is on; a call that touches no workstream path inherits them, a call inside the same work keeps what it does not name, and a call that names other work replaces them. **A Bash command is paired on its `tool_use_id`**: `PreToolUse` writes `telemetry/pending/<tool_use_id>.json` for a matched command while the switch is on, and `PostToolUse` or `PostToolUseFailure` reads it, writes one line for the call with its time and exit code, and removes it. The line names the first program the filter matches, and its `programs` key holds how many programs the call ran, so a call's time is summed once. A failed call writes its `events › closed` line too, under `PostToolUseFailure`. A start file older than 600,000 ms is removed when the next one is written, because no foreground call runs longer. The programs are `spnutils`, the plugin CLIs, `nx`, `git` and `docker`, and `.spndevex/.debug/telemetry/filter.json` adds or removes them. `packages/plugin-support-lib/src/lib/timing.ts`, `carryTags`; `packages/plugin-spn-devex/src/scripts/lib/bash-timing.ts`.
