## 1. Classify

| Class | Signature | Steps to run |
| --- | --- | --- |
| **BE-only** | New/changed capability with no surface change (a service rule, a queue flow, a migration, an internal method) | contract → service → entry → test → docs |
| **FE-only** | Surface change against an **unchanged** contract (page, component, nav, gating) | ui → test → docs |
| **Full-stack** | Contract surface changes and a surface consumes it | contract → service → entry → ui → test → docs |

Gates before starting:

- **Gate check.** Where the change adds or moves an authorization gate, settle what varies the answer before you write it. A rule that changes per person is a permission; per organization type, an enablement; per plan, billing. None substitutes for another, and an enablement never gates a read. `refs/platform/core/tenancy/permission-vs-enablement.md` in this plugin carries the question, the grammar and the traps; this plugin's `providers/ts/scripts/checks/_src/enablement-grammar.ts` refuses the checkable ones at write time.
- **Additive check.** If the change removes/renames/retypes a published field, changes a meaning, or tightens validation on an existing command field, it is **breaking**. Stop and reroute through the `ideate` skill (decision + versioning path). Additive by default is the rule, not a preference.
- **Ownership check.** The change lands in the module that owns the capability (its package, or the app-owned module). Cross-module needs go through the other module's **contract** services — or a request queue for writes — never its internals.

## 2. Read the installed platform surface — per step, on demand

The platform's capabilities are wired onto by **reading the installed contract surfaces directly** — never from memory. `.claude/saasplane/rules.md` (generated by `spnutils repo agent-sync`) lists *what* is installed; the contract layer of each installed package is *the* source for its surface:

- **contract step** — read sibling contracts of the owning module for state/command shape prior-art before adding new ones. Those are the `node_modules/@saasplane/module-server-<mod>-ts` contract exports, or the module's `src/contract/` when working inside the platform repo.
- **service step** — read the **contract services** of every module you must call (interfaces, commands/states, permission codes, queue topics). In-process contract calls for installed modules; the API client for remote ones. Never wire onto a method you have not read.
- **ui step** — read the API client's surface for the services the UI consumes, and the UI module package's (`MODULE_WEB`) exports for plug-in points.

Scope reads to what the step needs — the inventory tells you which packages exist; open only the relevant ones.

## A page is built from the tree of its pattern

The `ui` step follows this section for every page a change adds or rearranges. **The Surface rules are the spn-surface plugin's, and its entry ref, `refs/support/surface/README.md`, is the one way in: follow its route 3, *Build a screen*.** It reads the page's design tree first; with no tree, the design steps through the tree, shown before any code, and where the partner brings a design of the page or a page to follow, the design skill's given-design mode; then what a page writes for each unit on its stack, and what a unit does not do yet; then the choice tables, for every closed prop the page writes.

- **Start from the tree the `design` skill wrote.** It names the kind of person the app is for, the flow the page is a step of, the facts, the app pattern (or each section's site pattern) and every block by level, with the case each block follows. Where a page has no tree, run the `design` skill first, and show its result before any code. Never arrange a page while you write it, and never build it from a picture: a design the partner brings goes through the given-design mode into the tree first.
- **Build a kept line as kept.** Where the partner answered *keep yours*, the tree marks the line with the rule, their words and the date. Build it as they chose, and carry the reason into the code as one comment on that line. A review raises nothing on a kept line, and where the Surface check notes one, answer from the comment and leave the code as it is.
- **Build each line of the tree with the unit it names.** An app pattern is an arrangement of units that exist, and it is never a block of its own (`RULE.SUPPORT.SURFACE.048` · MUST · skill:spn-surface/design). So you write no component for a pattern, and no component named after one. The page composes the panels, the widgets and the components the design system already has.
- **Use one panel for each thing a person reads or saves as a whole** (`RULE.SUPPORT.SURFACE.116` · GUIDE), as the tree has it. Its sections are content parts, each under its own title, and never panels of their own. Two things that are read or saved apart are two panels. An editor with its preview is one panel, with each thing written beside what it becomes and the actions at the start of the footer (`RULE.SUPPORT.SURFACE.115` · GUIDE).
- **Give the page that reads a record and the page that changes it the same parts in the same order** (`RULE.SUPPORT.SURFACE.117` · GUIDE). A reading becomes a field, a block of source becomes an editor, and the footer with the actions is added. Nothing else moves.
- **Read the spec of the pattern for each screen class.** It shows where the parts sit at a desktop, at a tablet and on a phone. Its values are samples, and the page's own data takes their place.
- **Keep the choice the tree made for each part.** A part whose query takes a page, a text or a filter is `DSDataTable`, in the layout the tree names. Send its search and its filters to the server, in the read the table asks for (`RULE.SUPPORT.SURFACE.070` · MUST · skill:spn-surface/design). Never filter in the page over the records already loaded.
- **Keep a site section's eyebrows as its site pattern states.** A hero's state is a `PRIMARY` badge eyebrow and its stack is `OUTLINE` `DEFAULT` badge facts, a grid cell's eyebrow is its group or kind as text and a badge only when it says a state, and a plan holds one eyebrow, with a second word as a `PRIMARY` badge fact (`RULE.SUPPORT.SURFACE.371` · GUIDE) (`RULE.SUPPORT.SURFACE.372` · GUIDE) (`RULE.SUPPORT.SURFACE.373` · GUIDE).
- **Hold each small thing to its rule of content**, and each closed prop to its unit's choice table, through the entry ref's route 3. A state is a badge on the line of facts or at the end of the line, and the normal state shows none. The end of a line holds its actions, a badge, or both. A line that leads to a page shows the arrow where its end holds no action. A field a person enters is `DSForm.Field`, and a field a person reads is `DSDataUnit`.
- **Style the page with the app's own styles rule** (`refs/support/apps/providers/ts/03-structure.md`, "An app's own styles"). A repeated pattern is a component of the app's own, values come from the design system's tokens, and no selector reaches the design system's insides.

**Where a unit does not do a thing yet, report the gap, and never build a private copy.** The entry ref's route 3 names what a page writes for each unit on its stack, and what a unit does not do yet.

- **Build the page with what the unit does today.** Where a line of the tree waits for the unit, leave it as the unit draws it.
- **Name each gap in the report**: the unit, what it does not do, and the line of the tree that waits for it. The gap is then proposed to the design system, where one change serves every page.
- **Never write a second table, a second filter bar, a second sheet or a second header inside a module to close a gap.** A copy built inside a page gets none of the theme, the density, the accessibility or the translation the unit has. It also hides the gap from the stack that has to close it.
- **Where the page cannot be built at all without the missing part, stop at that line and say so.** The page waits for the unit.

## Write code the capability generator can read

`spnutils apps gen-symbols` describes a package from its **barrel**, and classifies each symbol by its **shape** and the estate's **naming grammar** — never by the folder it sits in. So the conventions below are not style: code that ignores them is generated correctly and then published as the wrong thing, or as nothing at all. This is the seam where the stack's skills and the stack's `spnutils` adapter meet — the skill writes what the adapter is built to recognize.

| Write it this way | So it publishes as | Ignore it and you get |
| --- | --- | --- |
| `I<Mod><Entity>Service` interface with methods | `SERVICE`, each method an `OPERATION` | a bare `TYPE` |
| `<Verb><Entity>Command` · `<Concern>Event` | `COMMAND` · `EVENT` | `STATE`, indistinguishable from a result |
| `<X>Entity` · `<X>Repository` · `<X>Controller` · `<X>Listener` classes | those roles, with join keys and routes | `UTIL` |
| `<Mod>ErrorCodeType` · `<Mod>PermissionType` enums | `ERROR` · `PERMISSION` | ordinary `ENUM` |
| `<MOD>_AUTHZ` const holding the gate table | the resolved permission set behind each reference | an unresolvable `authz` reference |
| `React.FC<I<X>Props>` or a `props: I<X>Props` parameter | `COMPONENT` | `UTIL` |
| `use<X>` | `HOOK` | `UTIL` |
| `@SPAuthorize(<MOD>_AUTHZ.<REF>)` · `@SPAPIRouteCommand('POST', '/path', …)` | the gate and the route on the operation | an operation with no cost and no address |

Three more that decide whether a symbol appears at all:

- **Only the barrel is read.** A file under a `_`-prefixed path segment, a declaration without `export`, and a `private`/`protected` member are each excluded. Those are the three ways to keep something out, and they are the *only* ways.
- **A one-line JSDoc intent is harvested** into the artifact (`RULE.SUPPORT.APPS.006` · MUST · skill:spn-apps/implement). No intent means the symbol is in the index with nothing to select it by — the single most common reason an agent cannot find work that already exists.
- **`@deprecated` travels.** Tag a superseded export and every consumer's agent sees it.

**The step files are the standard for anyone reading them** — generate against those, not against a document you may not have. Their provenance is the foundation book's TypeScript provider set — the standards chapters plus the kind registry and lifecycle seats. That set carries the reasoning behind each rule for readers who have it. Nothing in the steps is deferred to it.
