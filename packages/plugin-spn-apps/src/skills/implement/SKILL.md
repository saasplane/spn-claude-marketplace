Use whenever the user asks to build, add, change, or fix a feature or behavior in an SPN platform - it classifies the requirement (BE-only, FE-only, full-stack) and sequences the golden-path steps in contract-first order, contract, service, entry, ui, test, docs, closing with tests and the contract review gate.

# implement — classify, then walk the steps in order

**Read `refs/devex/workspace/workstream.md` (spn-devex) before acting.** It holds the loop this skill runs inside: how a prompt is read, where a new ask goes, what a prompt does to a running arc, and how a reply closes.

If the `ideate` skill ran, the design is already in the owning module's docs as `🔮 planned` rows (behaviors + capabilities) — read those rows back as the spec. Otherwise classify from the request directly.

## 1. Classify

| Class | Signature | Steps to run |
| --- | --- | --- |
| **BE-only** | New/changed capability with no surface change (a service rule, a queue flow, a migration, an internal method) | contract → service → entry → test → docs |
| **FE-only** | Surface change against an **unchanged** contract (page, component, nav, gating) | ui → test → docs |
| **Full-stack** | Contract surface changes and a surface consumes it | contract → service → entry → ui → test → docs |

Gates before starting:

- **Gate check.** Where the change adds or moves an authorization gate, settle what varies the answer before you write it. A rule that changes per person is a permission; per organization type, an enablement; per plan, billing. None substitutes for another, and an enablement never gates a read. `refs/platform/core/tenancy/permission-vs-enablement.md` in this plugin carries the question, the grammar and the traps; this plugin's `providers/ts/scripts/checks/_src/enablement-grammar.ts` refuses the checkable ones at write time.
- **Additive check.** If the change removes/renames/retypes a published field, changes a meaning, or tightens validation on an existing command field, it is **breaking**. Stop and reroute through the `ideate` skill (decision + versioning path). Additive by default is the rule, not a preference.
- **Ownership check.** The change lands in the module that owns the capability (its package, or the app-owned module). Cross-module needs go through the other module's **contract** services — or a request queue for writes — never its internals.

## 2. Read the installed platform surface — per step, on demand

The platform's capabilities are wired onto by **reading the installed contract surfaces directly** — never from memory. `.claude/saasplane/rules.md` (generated by `spnutils repo agent-sync`) lists *what* is installed; the contract layer of each installed package is *the* source for its surface:

- **contract step** — read sibling contracts of the owning module for state/command shape prior-art before adding new ones. Those are the `node_modules/@saasplane/module-server-<mod>-ts` contract exports, or the module's `src/contract/` when working inside the platform repo.
- **service step** — read the **contract services** of every module you must call (interfaces, commands/states, permission codes, queue topics). In-process contract calls for installed modules; the API client for remote ones. Never wire onto a method you have not read.
- **ui step** — read the API client's surface for the services the UI consumes, and the UI module package's (`MODULE_WEB`) exports for plug-in points.

Scope reads to what the step needs — the inventory tells you which packages exist; open only the relevant ones.

## 3. Walk the steps

**Each step is a file at `providers/{stack}/skills/implement/steps/{step}.md`**, and **the stack is the node's own, read from the nearest `sprepo.json` — never typed on a command and never assumed from a file extension.** This skill names the steps and their order; it never names a stack. Open them by composing that path.

| | Step | What it settles |
| --- | --- | --- |
| 1 | `contract` | states, commands, events, validators (`spnutils apps gen-validators`) |
| 2 | `service` | the canonical service shape: authz, transactions, cache, queues, audit, repository, migrations |
| 3 | `entry` | thin controllers, the route grammar, CLI controllers |
| 4 | `queue` | listeners, `subscriberId` as a consumption contract, why the handler is ungated, consumer-side idempotency |
| 5 | `ui` | `MODULE_WEB` plug-in points, hooks, permission gating (full-stack / FE-only) |
| 6 | `test` | how this stack runs each tier. **Which tier a project owes is `DEVEX_TEST`'s**, and that skill carries the ladder |
| 7 | `docs` | the doc set closes the change. **The seats, the two voices and the glossary are `refs/devex/workspace/docs/doc-sets.md` in the spn-devex plugin**; this stack's half is `env` — where a key goes in its env files |

**A step file this stack does not ship is a step this stack does not walk.** A realization that is absent says so; nothing here stubs one.

Order never changes; skip only what the classification skips. **Documents lead code** (`RD.DEVEX.WORKSPACE.081`): before the contract step, the owning seat already says what will be true — the `🔮 planned` rows `ideate` wrote, or rows you write first when it did not run. A part runs its documents, then its source, then its tests, then the close's run, never one function at a time. **Docs move with the steps, not after them.** The contract step updates `docs/04-capabilities/` rows and writes intent comments as it writes the surface. The test step writes behavior ids into case titles as each tier requires, and the docs step is the closing sweep that flips statuses. Regenerate at the marked points. Run `gen-validators` after any `contract/states/**` edit. Run `gen-barrel` after adding files to a lib package — never on apps or the API client. Regenerate the API client from the **running** service if routes or contracts changed before the FE consumes them.

**The test step proves each claim once, at the level that owns it.** Pick the tier by what would break: a validation rule breaks in a unit, an authorization gate breaks against the real service, an outcome breaks end to end. A unit test for something that only fails when wired is a green proving nothing. A journey re-checking a rule the contract tier already decided is a slower copy of an answer you have. **The tier decides which cases carry a behavior id** (`RD.DEVEX.FUNCTION.064`): every contract, component and journey case; every integration case proving a guarantee; a unit case only where it proves a row whose `Tier` is `UNIT`. A row's `Tier` equals the tier of the case that proves it. That is what makes the rows readable later.

## A page is built from the tree of its page pattern

The `ui` step follows this section for every page a change adds or rearranges. The rules are in `refs/support/surface/standards-patterns.md`, in this plugin, and each pattern's spec is in `refs/support/surface/patterns/`.

- **Start from the tree the `design` skill wrote.** It names the facts, the page pattern and every block by layer. Where a page has no tree, run the `design` skill first. Never arrange a page while you write it.
- **Build each line of the tree with the unit it names.** A page pattern is an arrangement of units that exist, and it is never a block of its own (`RD.SUPPORT.SURFACE.048`). So you write no component for a pattern, and no component named after one. The page composes the containers, the widgets and the components the design system already has.
- **Use one container for each thing a person reads or saves as a whole** (`RD.SUPPORT.SURFACE.116`). Its sections are content parts, each under its own title, and never containers of their own. Two things that are read or saved apart are two containers. An editor with its preview is one container, with each thing written beside what it becomes and the actions at the start of the footer (`RD.SUPPORT.SURFACE.115`).
- **Give the page that reads a record and the page that changes it the same parts in the same order** (`RD.SUPPORT.SURFACE.117`). A reading becomes a field, a block of source becomes an editor, and the footer with the actions is added. Nothing else moves.
- **Read the spec of the pattern for each screen class.** It shows where the parts sit at a desktop, at a tablet and on a phone. Its values are samples, and the page's own data takes their place.
- **Keep the choice the tree made for each part.** A part whose query takes a page, a text or a filter is `DSDataTableWidget`, in the layout the tree names. Send its search and its filters to the server, in the read the widget asks for (`RD.SUPPORT.SURFACE.070`). Never filter in the page over the records already loaded.
- **Hold each small thing to its rule of content** (`refs/support/surface/standards-core.md`). A state is a badge on the line of facts or at the end of the line, and the normal state shows none. The end of a line holds its actions, a badge, or both. A line that leads to a page shows the arrow where its end holds no action. A field a person enters is `DSForm.Field`, and a field a person reads is `DSDataUnit`.
- **Style the page with the app's own styles rule** (`refs/support/apps/providers/ts/03-structure.md`, "An app's own styles"). A repeated pattern is a component of the app's own, values come from the design system's tokens, and no selector reaches the design system's insides.

**A few things a pattern asks for are the page's to pass, and the unit then does the rest.** `architecture-widgets.md` and `architecture-containers.md` state each one.

| The pattern asks | What the page writes |
| --- | --- |
| the `LIST` layout on a phone | the page reads the live device, `useDSContext().device`, and lists `LIST` on a phone. `DSDataTableWidget` reads no device type, and follows the layouts its page lists each time it draws |
| a line of the `LIST` layout | the page gives each record as an item line, `DSItem`, with its title, its description and its facts. The table's rows carry no padding of their own and answer the pointer, so the page writes no padding and no hover. In a list the row carries the link, the chosen fill and the arrow, and the item line inside it carries none; `DSItem` takes no `selected` |
| the picture and the end of an item line | the page gives the picture to `media` as data of one kind, `ICON`, `ICON_MARK`, `AVATAR`, `AVATAR_GROUP` or `CUSTOM`, with no size (`RD.SUPPORT.SURFACE.130`). It gives what stands at the end, which is data, a badge, a count or a status and never an action, to `endNode` (`RD.SUPPORT.SURFACE.131`, `RD.SUPPORT.SURFACE.178`). The actions of a head are the other blocks of its header, and they take their size and look from the place. `DSItem` takes no `startIcon` and no `actions` |
| the record in view, beside a data table or under it | the page gives the id of that record as `selectedRecordId` in the `data` of the widget's config, usually read from the address. The widget holds no state for it (`RD.SUPPORT.SURFACE.125`) |
| a card drawn from data | the page gives `DSCardWidget` its `header`, its `parts` of the kinds `ITEMS`, `LIST` and `FREE`, and its `footer`. The widget places the head, the rows and the empty words, so the page writes no padding (`RD.SUPPORT.SURFACE.127`). The small head of a part takes `headerActions`, drawn as the head of a group (`RD.SUPPORT.SURFACE.181`) |
| subjects compared across the same settings | the page gives `DSComparisonWidget` its `subjects` (each with `actions` of its own where it has some, such as an Edit, drawn in its head), its `groups` of rows, each a data field's `config` with a value for each subject or a `CUSTOM` row with a `renderer`, and `differencesOnly`. The widget draws every value through `DSDataFieldView` and marks a value that differs from the most common value of its row, or from the subject `baselineKey` names (`RD.SUPPORT.SURFACE.181`, `RD.SUPPORT.SURFACE.184`, `RD.SUPPORT.SURFACE.193`) |
| a time shown as how long ago | the page writes `type` as `AGO` on `DSFormatDate` or `DSFormatDateTime`, and no time format where the app's is meant (`RD.SUPPORT.SURFACE.122`, `RD.SUPPORT.SURFACE.123`). A log of what happened shows the date and the time |
| the paging in the footer of the container | the page puts an element in `DSContainer.Footer` and gives it to the table as `settings.pagination.footerElement` |
| a value changed in its cell | the page puts `edit` on one column of the `TABLE` layout, and on the `LIST` layout. The value is text |
| a way back on the title line | the page gives `DSContainer.Header` the address to go back to, and the header draws the back action before its title, level with the line of the title (`RD.SUPPORT.SURFACE.108`). No core unit places the two parts of a page of groups and their items (`RD.SUPPORT.SURFACE.099`). On the web, the stack's own `DSListDetailWidget` places them, and its `listWidth` is the named choice for a narrow part of groups (`RD.SUPPORT.SURFACE.119`). A page writes no width |
| the head of a page that holds several containers | the head stands above the containers, outside any frame, as an item line at the level `PAGE` with its way back. The page gives the title and the address to go back to, and writes no row, no back button and no padding (`RD.SUPPORT.SURFACE.120`) |
| tabs in a `flush` part | the page writes no padding for the tabs or for their panel. The tabs place their first tab and their panel by the inset of their place (`RD.SUPPORT.SURFACE.118`) |
| the head of a page, or of a part of a page | the title of a header is an item line. A container that is the whole page says so with `fullPage`, and its header is then the page head (`RD.SUPPORT.SURFACE.179`); any other box gives the level of its kind: `CONTAINER` for a container or an overlay, `WIDGET` for a card, `GROUP` for the head of a part of a card widget (`RD.SUPPORT.SURFACE.107`). The item line takes no `size`, and the heading element follows the level (`RD.SUPPORT.SURFACE.106`). A page that holds several containers writes `DSPageLevel` with the level `PAGE` and the part `HEADER` for its head (`RD.SUPPORT.SURFACE.178`). The page writes no type step and no heading element |
| the padding around what a card holds | the page writes none. A part of a card pads itself, from the size of the card. The page writes `flush` on a part whose content reaches the edge of the card, such as a list or a picture. A card hands its size to what it holds (`RD.SUPPORT.SURFACE.114`) |
| where a title starts | the page writes no prop and no padding. The part that holds an item line at the level `PAGE`, `CONTAINER`, `WIDGET` or `GROUP` gives it no padding at its two sides, and in a `flush` part the inset of its place (`RD.SUPPORT.SURFACE.109`). An item line draws no padding or highlight of its own, and a page writes no `bleed` (`RD.SUPPORT.SURFACE.175`) |
| a confirmation before an act | `DSConfirmPopover` for an act a person can undo, such as activate, deactivate or remove from a list, and `DSConfirmDialog` for an act that cannot be undone, such as delete. Both stay open while the act runs |
| the actions that close the work of an entry | over the page, in a dialog, a sheet, a drawer or a popover, the page puts them at the end of the footer, the action that leaves first and the main action last. In an entry that is a page of its own it puts them at the start of the footer, the main action first. A value changed in place keeps its two actions beside the box, the one that saves first. The main action is a solid button and the action that leaves is an outline button |
| an empty message of the data table | plain text, which the table draws as `DSEmpty` with the text as its title and a default icon. A page that needs a description or an action there gives its own `DSEmpty` |
| a sheet a person works in while the page stays usable | the page turns `modal` off on `DSSheet`. The sheet then stands beside the page and draws no scrim. On a phone it stays modal |
| a row or a grid of blocks in a part | the page writes it, with its gap from the scale, or uses a unit for it where its stack provides one. The foundation defines no block for it |
| a medium entry on the full screen on a phone | nothing. `DSSheet` takes the full screen on a phone by itself |
| fewer fields in the filter bar at a tablet | nothing. `DSFilterBarWidget` holds fewer by itself, and `moreLimitTablet` sets how many |

**Where a unit does not do a thing yet, report the gap, and never build a private copy.** `architecture-widgets.md` says plainly what a unit does not do, under *Not there yet*. Today that is:

| The unit | What it does not do yet |
| --- | --- |
| `DSDataTableWidget` | it changes a value in its cell only where the value is text. A choice, a date or another kind is not changed in a cell |
| a strip of steps | the design system has no unit for one, which A record and its steps draws as plain words |

- **Build the page with what the unit does today.** Where a line of the tree waits for the unit, leave it as the unit draws it.
- **Name each gap in the report**: the unit, what it does not do, and the line of the tree that waits for it. The gap is then proposed to the design system, where one change serves every page.
- **Never write a second table, a second filter bar, a second sheet or a second header inside a module to close a gap.** A copy built inside a page gets none of the theme, the density, the accessibility or the translation the unit has. It also hides the gap from the stack that has to close it.
- **Where the page cannot be built at all without the missing part, stop at that line and say so.** The page waits for the unit.

## 4. Close

- **Run the conformance gates** — the `verify` skill code mode: codegen freshness, `spnutils apps validate`, build, lint, tests. This is what catches a file whose name no longer matches its contents. It also catches a barrel that was never regenerated, or a reach past another module's contract. A passing build reveals none of them.
- **Run the tests** — the `run` skill tests mode. Typecheck the touched projects first: `npx nx run <project>:typecheck`, and `npx tsc --noEmit -p <project>/tsconfig.json` for a web app, whose `typecheck` target is disabled.
- **Contract review gate** — if the contract surface changed, run the `review` skill contract mode before calling the work done. Code review (the `review` skill code mode) for everything else.
- Report what changed per layer, what was regenerated, and test results. For a page, name its page pattern and each gap of a unit the page met. Never claim green without having run the commands.

## Lenses

The step files are the `server-dev` and `web-dev` lenses worn — they carry the same rules. Additionally wear the spn-devex plugin's `refs/devex/agent/lenses/trust.md` on any mutation and `refs/devex/agent/lenses/partner.md` on contract states. The close's review gates are the panel convened: `partner` when the published surface changed, `trust` when authorization, audit, or secrets moved, `ux` when a page changed, `qa` always.

## Write code the capability generator can read

`spnutils apps gen-symbols` describes a package from its **barrel**, and classifies each symbol by its **shape** and the estate's **naming grammar** — never by the folder it sits in. So the conventions below are not style: code that ignores them is generated correctly and then published as the wrong thing, or as nothing at all. This is the seam where the stack's skills and the stack's `spnutils` adapter meet — the skill writes what the adapter is built to recognize.

| Write it this way | So it publishes as | Ignore it and you get |
| --- | --- | --- |
| `I<Mod><Entity>Service` interface with methods | `SERVICE`, each method an `OPERATION` | a bare `TYPE` |
| `<Verb><Entity>Command` · `<Concern>Event` | `COMMAND` · `EVENT` | `STATE`, indistinguishable from a result |
| `<X>Entity` · `<X>Repository` · `<X>Controller` · `<X>Listener` classes | those roles, with join keys and routes | `UTIL` |
| `<Mod>ErrorCodeType` · `<Mod>PermissionType` enums | `ERROR` · `PERMISSION` | ordinary `ENUM` |
| `<MOD>_AUTHZ` const holding the gate table | the resolved permission set behind each reference | an unresolvable `authz` reference |
| `React.FC<I<X>Props>` or a `props: I<X>Props` parameter | `COMPONENT` | `UTIL` |
| `use<X>` | `HOOK` | `UTIL` |
| `@SPAuthorize(<MOD>_AUTHZ.<REF>)` · `@SPAPIRouteCommand('POST', '/path', …)` | the gate and the route on the operation | an operation with no cost and no address |

Three more that decide whether a symbol appears at all:

- **Only the barrel is read.** A file under a `_`-prefixed path segment, a declaration without `export`, and a `private`/`protected` member are each excluded. Those are the three ways to keep something out, and they are the *only* ways.
- **A one-line JSDoc intent is harvested** into the artifact (RD.SUPPORT.APPS.006). No intent means the symbol is in the index with nothing to select it by — the single most common reason an agent cannot find work that already exists.
- **`@deprecated` travels.** Tag a superseded export and every consumer's agent sees it.

**The step files are the standard for anyone reading them** — generate against those, not against a document you may not have. Their provenance is the foundation book's TypeScript provider set — the standards chapters plus the kind registry and lifecycle seats. That set carries the reasoning behind each rule for readers who have it. Nothing in the steps is deferred to it.
