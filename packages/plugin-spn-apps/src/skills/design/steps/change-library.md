# Step: change-library — a change of a library file, through the connector

Read this step when the library lacks a block, a property or a value, and the window holds the Figma connector. **Every rule is stated in `refs/support/surface/delivery-library.md`, under the heading each line names.** A line here says what to do, and the heading says why and how far it holds. Read the heading before you do the line.

Its provenance is the foundation book's design library chapter. Apply this restatement. The chapter is provenance, and not a file to open.

## What the library draws, and what it does not

- **The library draws the core units, which are the ones the book names** (`RD.SUPPORT.SURFACE.082`). A change of the surface is stated in the book first, drawn in the library second and built in a stack third, and that order binds a core unit and its props. Heading: "Changing the library".
- **Never draw a unit that a stack provides on its own as a published component.** The book does not name it, so the library does not draw it, and the order does not bind it. Where an order asks for one, stop and report it. A stack's own unit that every stack should build joins the book first, and the library draws it then.
- **Never put a page or a pattern into a library file** (`RD.SUPPORT.SURFACE.099`). The library draws the core units with their properties and their cases, the icons, and the places of the layout, and nothing else. It holds no task pattern, no page pattern, no skeleton and no sample page. A pattern is built from units, so it is composed on request from the published library, in a file that is not a library file. Heading: "Three kinds of work".
- **Name a unit so that its name says its layer** (`RD.SUPPORT.SURFACE.098`). A widget's name ends in `Widget`, a container's in `Container` and a layout's in `Layout`. A component takes no such word, and no block carries a letter for its layer before its name. A name that belongs to a unit keeps the unit's whole name first: `DSFilterBarWidgetField` is the item of `DSFilterBarWidget`, and `.DSDataTableWidgetEmpty` is a private part of `DSDataTableWidget`.
- **A core unit that is put together from other blocks, or that opens something the device draws, is drawn as the table under "Drawing a block" says.** An item of `DSToolbar` is an instance of `DSButton` in a slot, and a tag of `DSTagGroup` is an instance of `DSBadge` with its close action, so neither has a variant for what it holds. `DSCalendar` is drawn once, as the grid that `DSDatePicker` opens. `DSColorPicker` is the swatch and the field, with a colour, with none, and with a typed text that is no code, and the picker of the device is not drawn. `DSColorView` is the swatch and the value, the swatch alone, and the empty case. `DSProgressCircle` is the ring at each size, filled to a value and turning. `DSMark` holds `shape`, `variant`, `size` and `scaleSize` as properties, and `color` as a mode. `DSConfirmPopover` is its surface alone, with the question and the two actions, and the control that opens it is not part of the drawing. `DSConfirmDialog` is its surface alone, over `DSBackdrop`.

## The walk, in order

1. **Read the file once, by passing `skills/design/scripts/page.js` to the connector as it is with its inputs filled, or take the inventory you were handed, and write the time of the reading on it; where the inventory is for the tool, read the file with `skills/design/scripts/inventory.js` (the list of pages first, then one call for each page) and `skills/design/scripts/tokens.js`, save each answer as a file in one folder, put them together with `node skills/design/scripts/assemble.mjs --answers <folder> --out <inventory>`, and take that in with `spnutils apps surface library --file <inventory>`; before you take it in, prove each unit by a hash: send the same script again inside a function with its body unchanged, have it return an eight-character hash for each unit, compute the same hash from the answer file, and compare by program.** Headings: "The inventory", "How the connector's work is carried out", and "What the agent reads and keeps".
   - **`page.js` stops by its byte limit on a large page.** It answers what fits under `maxBytes` and names where to go on in `next`: at `maxBytes` 15000 to 16000 one answer held 49 to 70 nodes, of pages of 88 to 367. Read the rest with a short read-only script of your own, limited to the section you work in, and do not send `page.js` for range after range. `page.js` gives no key, no mode and no binding, so the same short script reads those.
   - **`page.js` and the scan do not see a component that stands inside a plain frame.** Their walk goes down through sections and no further, so the 56 icons of the Core file's Icons page count as one reference frame. Read such components by their ids.
   - **`assemble.mjs` refuses a folder with no answer of `tokens.js`.** Read `tokens.js` for every library file, also one that holds no variable and no style, whose answer says `itemCount` 0. With `--out` inside the answers folder, a second run would read the inventory as an answer, so assemble a folder once.
   - **`check-answers.mjs` proves nothing over the answers of `inventory.js`.** It reads only answers that carry `rows` and a `hash`, which are the answers of `versions.js` and `instances.js`. Over a folder of `inventory.js` answers it prints `0 answers, 0 pages, 0 failures` and exits 0. The proof of an inventory is the hash of each unit that this step states.
2. **Ask the developer for a named version before the first change in the file, and wait.** Heading: "Before a connector writes".
3. **Check the order against the live file, and against the web's file and line, and say what you corrected.** Heading: "Before the change".
4. **Tell the developer what is about to change, item by item.** Heading: "Before a connector writes".
5. **Send one script for each page, given the nodes it may touch, and let it check before it moves anything and return its own proof.** Where the script makes a frame a slot, follow the connector's facts under Slots, and where it draws a group whose members are joined, follow the facts on the joined look. Headings: "During the change", "How the connector's work is carried out", and "The connector's facts".
6. **Before you add a property or a value to a set, work out the versions the set will hold, never pass 1,000, and draw a look the stack shows as one case as a case on the unit's sheet.** Heading: "Versions that are added are laid out".
7. **Where a call moves versions, lay out one set by passing `skills/design/scripts/layout.js` to the connector as it is, dry first, and read the default version of each set before and after, check it against the stack's default at the top left, and correct a label that disagrees, never follow it.** Headings: "The default version is the stack's default, and the label tells the truth about it", and "How the connector's work is carried out".
8. **Draw, for each unit, what a person sees of it: a usage of its primary use for every top-level unit (a part owes none); every property that changes what is visibly there, placed by the section of the unit's page in the showcase that shows it (a set crosses its `size`, its states and the shared `variant`, and no other property; every other property is a case named `<property>=<value>` on the unit's sheet of cases, the Cases of the showcase, and a look that no property can produce is a version drawn once, crossed with nothing), a property that is on by default by its off case; a mode, shown by one case, for a property whose value is a token; every state the unit can be in (open, hover, focus, pressed, selected, checked, filled, invalid with its message, disabled, loading, empty), a property that lets a unit reach a state by that state; and, for a property of behaviour, which changes nothing a person can see in any state, a note in the header, ` · behaviour: <property>, <property>`.** A unit drawn as cases alone says why in its sheet's label. Place a property from the web's source and the running showcase, never from its name. `disabled` stays a property of its own and is never a value of `state`; a pair of values the web cannot be in is left out; the hue is a mode set on the instance, shown by one case. Headings: "What a library file owes of a unit", "Which property is a variant and which is a case", and "The form of a label".
9. **Give a new set, sheet or page the form of its neighbours, place a case as instances of the unit, and say on the sheet's label what a unit cannot hold, and list it.** Headings: "A new set, sheet or page takes the form of its neighbours", "A sheet of cases, and a case", "A unit that cannot hold the web's case", and "A unit with no look of its own".
10. **Put every thing a unit owns inside the unit's section, in the book's order: the header, the set with its row and column labels, the usage, the cases and the parts, with a page's top level holding sections only.** Name the header's layer `header · ` and the unit's name, and every other label's `label · ` and its text, and a sheet's label stands above the sheet in the band of cases and is never the header. A unit drawn only as a sheet of cases gets a section with its header and its sheet, the header's layout clause reading `no set of versions, shown as cases`. Begin a usage's layer and caption with `usage · ` and the unit's name, with no comma after it, centre a row label on its row's band, give a thing room for what it draws, and give a section the fill its page's content stood on. In the Core file a section holds a group of tokens with one frame of specimens, and a frame that sets a variable mode moves whole. Headings: "A file's pages are the showcase's groups, and a unit is one section", and "A section of the Core file". **Place the pieces of a page's sections at the book's distances by passing `skills/design/scripts/align.js` to the connector as it is, in mode `plan` first and then `run`:** it moves and resizes only the sections and the pieces directly inside them, and proves the page's alignment (the header at the padding, each band 80 apart, nothing outside its section or meeting another, every label's offset from its set kept) against a ledger it takes before the change.
    - **On a page of about 140 sets and lone components or more, send `plan`, then `apply`, then `prove` in a call of its own, and never `run`.** In mode `run` the answer carries one ledger line of about 140 characters for each set and lone component, so it passes the connector's limit of 20,480 bytes at about 140 of them (about 26,000 characters for 189). An answer past the limit is refused and the call's changes are not kept (connector rule 21). Mode `ledger` with `what: "lines"` has the same limit. So before `apply`, read the ledger with a short read-only script that holds the ledger functions of `align.js` word for word and returns each line as its id and its hash, with the label offsets and the hash of the order, and pass it as `ledger` to `prove`: each answer is then under 3,000 characters. `run` answered whole on pages of 42 and of 75.
    - **`align.js` does not read a section of the Core file.** It reports the frame of specimens as the anomaly `above no band label` and plans a section that ends under the label. Plan it there if you want its reading, and never apply it on a Core page.
    - **Neither `align.js` nor a scan part reads the order of the layers panel.** `align.js` sorts the top-level sections by their place on the page, takes no order as an input and never changes the order of layers, and its `order` hash stays the same when a section moves in the panel. Read `page.children` and each section's `children` yourself: the panel reads from the last child to the first. A section out of the showcase's order on the page is moved first, by its exact id.
    - **A header that grows in a part's section owes `align.js` on that page.** A part's section is only as wide as its widest piece and the padding, so a longer header passes its section's edge (two headers 121 longer stood 41 outside, and `align.js` made each section 121 wider).
11. **Make a new unit in a section of its own at the end of its group's page, put a label or a usage in its unit's section, and a part in the section of the unit that owns it or in Shared parts.** Heading: "A file's pages are the showcase's groups, and a unit is one section".
12. **Read a set's key, its versions' keys, its name, its size, its default and its properties before a move into a section and after it.** Heading: "A file's pages are the showcase's groups, and a unit is one section".
13. **Take one picture for each set or sheet, and look at it.** Headings: "How the connector's work is carried out", and "What the agent reads and keeps".
14. **Scan the whole file last, a page at a time, with the four parts of the scan: `skills/design/scripts/scan-labels.js`, `scan-placement.js`, `scan-properties.js` and `scan-sets.js`, each passed to the connector as it is with its inputs filled, one part for each call.** The scan is one scan cut in four so that no call nears the limit of 50,000 characters, and a part is never sent in a shape other than as it is; a page is clean when all four parts say `clean`, and `only: "<finding>"` asks a part for one finding whole. A part reads a page of either form (nodes at its top level, or inside sections) and says which in `form`; a page where it found no unit answers `emptyReading`, never `clean`. Beside the findings of old it reports a top-level node that is no section, things inside a section that meet, a thing outside its unit's section, a section whose pieces stand out of order, a unit with no header, a usage that names no unit, and a child that lies outside its section's box (by its box or by what it draws, with the side and the px); it blocks on a top-level unit with no usage (a unit drawn as cases alone, with no component in its section, takes its first case for its usage) and on a boolean, swap or text property that nothing on the page draws off its default and that the header does not name after `behaviour: `; it counts, without blocking, the top-level units that have no sheet of cases (a unit whose versions draw everything owes none), and names a property that the clause names and the unit holds, because the book says a property of behaviour is not held by the set (`behaviourNamesHeldProperty`); and it reads a sheet's label apart from a header and a default mark by the words of a value before its first `: `. Heading: "Before a publish".
    - **On a page of the Core file only `scan-labels.js` answers `emptyReading`.** `scan-placement.js`, `scan-sets.js` and `scan-properties.js` answer `clean: true` there having read no unit, because the scan stops at a plain frame. Do not take that `clean` for a reading.
    - **No scan part reads the order of the layers panel,** as step 10 says of `align.js`. Read it yourself.
15. **Tell the developer what changed, what still differs from the web and was left, and that the publish is theirs.** Where the file has taken a library's update, read its sets again and run the layout proof and the scan again before you say anything is whole. Before you tell the developer anything is whole, close the loop against the code yourself: re-read the page you changed with `inventory.js`, take it in again with `spnutils apps surface library --file <inventory>`, and run `spnutils apps surface gaps <package>` for the stack the unit belongs to. A unit you just drew that still shows as a gap means the drawing did not match what the stack's own snapshot expects — read the gap and fix the drawing, not the stack, unless the gap is a real difference you are telling the developer about. Headings: "Before a publish", and "The connector's facts", under A library's update.

## Adding a property, a value or versions to a set

Step 6 and step 8 say what a set must hold. These steps say how one is grown, in order. Each has its reason after it. Headings in the reference: "Versions that are added are laid out", "A label", "The form of a label", "A sheet of cases, and a case", and "The connector's facts".

1. **Read the set again just before the first change.** A writer may have changed it since the inventory was read.
2. **Work out the versions the set will hold, and say so.** One more property multiplies them, and 1,000 is the limit.
3. **Give a new property a default value that draws what stands.** The versions that are there are then the look of the default, only the other values are new drawings, and no placed instance changes.
4. **Make each new version as a copy of its nearest twin, and change only what its value changes.** Name it `property=value, property=value`, with no comma inside a value. A copy made inside a set loses its property ties, and a slot in it becomes a plain frame, so compare each copy with its twin and tie it again. A copy keeps the variable bindings of its layers, so bind nothing again. A slot made again as a copy of the twin's slot stays a slot and loses its ties too, so tie it again in the same call.
5. **Keep the default at the top left.** The default version is the one at the top left of the grid, and not the first child. Change it by changing places in the grid, and read it back before and after.
6. **Rename a property or a value in the versions' names.** The versions keep their ids and keys, so nothing placed breaks.
7. **Grow the set, its section and its sheet so that nothing meets.** A copy lands on the version it was made from, and a section that is too small leaves a thing outside it. Then run the layout script, dry first.
8. **Set a label's text and its layer name in one step.** The layer is `label · ` and the text, so a script reads the unit from the label.
9. **Name a case `property=value`, with no comma inside a value,** and keep the name unique on its sheet.
10. **Make the unit's header name the new property.** Its layout clause and its default marks must say what the set now holds, or the scan reports the header as wrong.
11. **Take the hashes of the set before and after, and list every difference.** A difference that your order did not name is a finding to report, not to keep.
12. **Do only what your order names, and report the rest.** A writer that meets a fault outside its order writes it down and leaves it. The permission check refuses a call that changes a library when the order did not name the change.

13. **Append a copy of a label or a case to its section or its sheet, and set its place again.** `clone()` of a text or a case component lands on the page's top level, not in the parent of the node it copies. Move the copy into the unit's section (a label) or onto the unit's sheet (a case), then set its `x` and `y`.
14. **Put a new property's cell in a version's name where its neighbours put it.** Read a neighbour of the same group on the page: `size` goes first in the names, and any other property follows the order in which the header's clause names them. Say which order you took.
15. **Say when a property is drawn at one format only.** Where a property such as `size` is drawn only at the default value of another (a size other than SM at the default format), make it the outer axis of the rows, fill only that column, and end the header with a note that says so (`disabled=true only at rest` is the form).
16. **Prove that the old versions are untouched by a hash of each version, not only by the set's ledger line.** The ledger line (id, key, size) does not show that a version is the same inside. Hash each version's layers before the change and after it, and list the versions whose hash differs.
17. **Keep a row label inside the room it has.** The book puts a row label's right edge 24 left of the set. A longer label moves its left edge towards the content line, and one too long would move every set on the page. Report a label that would pass the line, and shorten its text, never move the sets.

## A set changed by its spec

Read this walk when a unit has a spec (one JSON file for the unit: `unit`, `setId`, `keep` or `remove`, `dropProps`, `move`, `defaults`, `header`, `cases`, `expect`) and the set is to be brought to it. The scripts are in `skills/design/scripts/`; every one that changes the file is dry by default and takes `dryRun: false` for the real call (connector rule 19). `cases.js` and `labels.js` have run against a file, dry and real, and the real answer matched the dry one; a dry answer is still read line by line before the real call is sent.

**Send a page's changes together.** Where a page holds more than one set to change, do not send a script once for each set. Write an inputs file for the page, a JSON list with one filling of the script's inputs for each set, and make one call of it: `node skills/design/scripts/bundle.mjs --script <name.js> --inputs <file.json> --out <prefix>`. The call holds the script's own body once and runs it for each entry, so a page costs one dry call and one real call for each step below, whatever the number of its sets. Every run of one call works on the same page; a unit placed on another page gets a call of its own for that page. Prepare the inputs by a program from the specs and the readings, never by hand, and prove the page at its end by a hash of each set's versions (their keys and names) against the hash the specs give. A bundled call that says `stopped`, or an answer that says `more: true`, is sent again as it is.

**What a unit still owes after its spec is carried out** is written as operations, and five more scripts carry them out (the walk for writing them, preparing a page's calls and sending them, the composing that follows, and the scan as one pass are in `skills/design/steps/operations-and-composing.md`; read it when a unit owes more than its spec), each dry by default and safe to send twice (what stands is reported as `stood`): `names.js` changes the versions' names, `copy.js` adds versions as copies of their twin and ties again what a copy lost, `property.js` adds a yes-or-no or a text property and ties its layer, `header.js` writes the header's layout clauses and ends it with the unit's notes, `sheet.js` makes a sheet for a unit that has none, and `cases.js` makes the cases, each with its properties and, where it has them, a text, a variable mode or a component of the sheet to take the place of. Send them in this order: names, copy, property, header, layout, labels, sheet, cases. Each refuses before it changes anything, so read its dry answer for `problems` first. Each has run against the file, dry and real, and its real answer matched its dry one.

1. **Have the developer save a named version first, and wait** (step 2 of the walk above).
2. **Check the specs offline, with no call to Figma.** Read the file's units with `versions.js` and `instances.js`, prove the answers with `check-answers.mjs <folder> <joined file>` (it reads only these two scripts' answers, which carry `rows` and a `hash`), and run `node skills/design/scripts/check-specs.mjs --specs <specs folder> --readings <readings folder>`. Go on only when it says `0 with faults`.
3. **Carry the spec out with `apply-spec.js`, dry first, then for real, one page in a call.** The connector works on one page at a time, so a unit that is placed on other pages gets one call with `steps: ["move"]` and `pageId` for each of them first. Only then, on the set's own page, send `move`, `remove`, `rename` and `header`. The moves on other pages come before the removal, because a version that still has an instance is not removed. A call that stops by itself says `more: true`: send it again.
4. **Lay the set out with `layout.js`, dry first, then for real,** and read the default version before and after. Its `defaults` are the spec's `layoutDefaults` where the spec gives them (the default of the set as it stands after the removal), or else its `defaults`; its `padding` and `gap` are read from the set's grid before the change. `layout.js` reads the header as a full cross, so a spec's `header` names every property the set holds once, with every value, and says nothing else inside `rows:` and `columns:`; `check-specs.mjs` checks that offline. A set that loses no version and no property is not laid out again. Keep `setBoxBefore` from the answer.
5. **Write the labels again with `labels.js`, dry first, with `oldSetBox` set to the `setBoxBefore` of the layout.** It reads the rows and columns from where the versions now stand, and refuses when the header names no layout or a row holds two values for a named property. Without `oldSetBox` it looks for the old labels beside the set as it is now, and the labels of rows a smaller set no longer reaches are left standing.
6. **Make the cases with `cases.js`, dry first.** It makes what the set's own properties can produce and reports in `problems` what it cannot (a swap, a missing sheet); draw those by hand.
7. **Place the page with `align.js`, mode `plan` first and then `run`.** On a page of about 140 sets and lone components or more, send `plan`, `apply` and then `prove` in a call of its own, as step 10 of the walk above says.
8. **Scan the page once, at its end, with the four parts of the scan.** `crossedBeyondTheRule` blocks a set that crosses a property outside the rule. `passedByException` in `scan-sets.js` counts the sets that pass only because a property is a known exception awaiting the developer's ruling, or because the book names the property for that unit (the table "A property a named unit keeps crossed", kept in `PROPERTIES_A_UNIT_KEEPS_CROSSED`, which passes a property for its own unit only); report that number.

## The measure and the pace

- **A library is brought to the web by its properties, its values, its defaults and its states, and by nothing clipped or overlapping.** This is the book's own rule: "A property that changes what is visibly there MUST be drawn", and a state a unit can be in MUST be drawn (step 8). Anything finer than that is listed in the report and not drawn. The developer decided this on 2026-10-09.
- **One writer takes a page whole, and a page is scanned once, when it is finished.** Two agents never change one library file at once. Scanning after each set costs a read of the page each time and proves what the last set's proof already returned. A page that is changed in two rounds, by its specs and then by hand, is finished after the second: `align.js` and the scan run once then, and the first round is proven by the hash of each set and a picture of each changed section.
- **The cost of a page is its calls, not its sets.** A writer writes each call's text out, so a script sent once for each set is paid for once for each set. Measured on DS 2-Components on 2026-10-09: a page sent set by set, with its alignment and scan, about 300 thousand tokens; the same work as bundled calls, with the alignment and the scan left to the page's end, about 100 thousand, in ten calls.
- **Closing a page costs the same whatever the page holds, and composing costs by the line.** Closing a page (the alignment twice and the four scan parts, about 150 thousand characters sent whole) costs about 100 to 200 thousand tokens, so one agent composes a page and another closes it. A composed line or look costs 15 to 30 thousand tokens. Measured on DS 2-Components on 2026-10-10.
- **One closer finishes a file when its drawing is done, where the pages only gain versions inside sets.** On such a page a set, its sheet and its section grow, and nothing else changes. So each writer proves its own sets by their ids, their keys and one picture of each, sends no `align.js` and no scan part, and ends its report with what grew. The closer then takes each changed page once: `align.js`, and the four scan parts. A page is still scanned once, and the whole file is still scanned before the developer is told it may be published (step 14). The fixed cost of closing is then paid once for a page, however many writers changed it.
- **What a writer reads before its first call is paid for by every writer.** A writer that is handed `skills/design/steps/writer-brief.md` and its order reads two pages, and it opens a long step only when it is stuck. Measured on DS 2-Components on 2026-10-13: two writers that were handed the brief and one order, and closed no page, used 164 and 167 thousand tokens. Writers that were handed six documents to read whole, and closed their page, used 350 to 750 thousand tokens on rows of the same size. The measure holds the brief and the one closer together, and it does not say how much each saved.
- **The model of a child follows its work.** Work that its order states whole goes to the smaller model: a rename, a layout after a resize, a check, plain copies and an inventory. A shape and a new look go to the larger model. The developer agreed to this on 2026-10-13. No measure of it stands: both writers measured on that day ran on the larger model.

## A child agent

A child agent that sends `use_figma` cannot read the connector's own skill, so this skill carries the rules a child needs.

- **Hand a writer `skills/design/steps/writer-brief.md`, the order for its work and the file's inventory.** The brief restates what a writer of one page needs from `skills/design/steps/connector-rules.md`, from this walk and from `skills/design/steps/operations-and-composing.md`. The writer opens one of those only when it is stuck, which is when it meets a thing the brief does not cover or a call fails in a way it cannot explain. Its report says which step it opened and why. The order names what the brief leaves to it: the page, the nodes the writer may touch, the web's file and line for each thing it makes, and the path of its report.
- **Hand `skills/design/steps/connector-rules.md` whole to a child whose work the brief does not cover.** For operations, composing or the scan, hand it `skills/design/steps/operations-and-composing.md` too, and say which part it is (a composer, a closer or a reader).

A child sends nothing the order does not name.

Never edit the body of any script: fill its inputs and pass the rest as it is.

Keep the inventory current as you go: a change to the file updates the inventory's lines for what it changed.

**The connector cannot publish a library, and it never does.** The developer publishes after your word.
