# Step: change-library — a change of a library file, through the connector

Read this step when the library lacks a block, a property or a value, and the window holds the Figma connector. **Every rule is stated in `refs/support/surface/delivery-library.md`, under the heading each line names.** A line here says what to do, and the heading says why and how far it holds. Read the heading before you do the line.

Its provenance is the foundation book's design library chapter. Apply this restatement. The chapter is provenance, and not a file to open.

## What the library draws, and what it does not

- **The library draws the core units, which are the ones the book names** (`RULE.SUPPORT.SURFACE.082` · MUST · skill:spn-surface/design). A change of the surface is stated in the book first, drawn in the library second and built in a stack third, and that order binds a core unit and its props. Heading: "Changing the library".
- **A design change is a proposal in Lab, and the library files are drawn again only after the web has it.** A designer, or you through the connector, changes a unit in Lab; the comparison lists it as held by the library and lacked by the stack; the web is built to it, released, and the showcase shows it; the next run reads each cell from the showcase into its record and draws it from the record, so the library and the web match. A run never draws an old look over a proposal. Heading: "Changing the library".
- **Never draw a unit's look by hand** (`RULE.SUPPORT.SURFACE.411` · MUST · skill:spn-surface/design). Each planned cell is read from the running showcase's Main page of the unit into its record, and the plugin draws the cell from the record (`RULE.SUPPORT.SURFACE.422` · MUST · skill:spn-surface/design). A token that names no variable is drawn as its value and reported, never left unnoted. After a page is drawn, run `gaps` and read it back through the connector against its plan, and fix each gap in the plugin's drawing, the record or the plan, never the page by hand beside the set. Heading: "The path of a page through the connector".
- **Never draw a unit that a stack provides on its own as a published component.** The book does not name it, so the library does not draw it, and the order does not bind it. Where an order asks for one, stop and report it. A stack's own unit that every stack should build joins the book first, and the library draws it then.
- **Never put a page or a pattern into a library file** (`RULE.SUPPORT.SURFACE.099` · MUST · skill:spn-surface/design). The library draws the core units with their properties and their cases, the icons, and the places of the layout, and nothing else. It holds no task pattern, no app page kind, no skeleton and no sample page. A pattern is built from units, so it is composed on request from the published library, in a file that is not a library file. Heading: "Three kinds of work".
- **Name a unit so that its name says where it is placed** (`RULE.SUPPORT.SURFACE.229` · MUST · skill:spn-surface/design). A suffix is `App`, `Layout`, `Page`, `Container` or `Widget`. A component, a composite included, takes none, and no block carries a letter for its layer before its name. A name that belongs to a unit keeps the unit's whole name first: `DSFilterBarField` is the item of `DSFilterBar`, and `.DSDataTableEmpty` is a private part of `DSDataTable`.
- **A core unit that is put together from other blocks, or that opens something the device draws, is drawn as the table under "Drawing a block" says.** An item of `DSToolbar` is an instance of `DSButton` in a slot, and a tag of `DSTagGroup` is an instance of `DSBadge` with its close action, so neither has a variant for what it holds. `DSCalendar` is drawn once, as the grid that `DSDatePicker` opens. `DSColorPicker` is the swatch and the field, with a colour, with none, and with a typed text that is no code, and the picker of the device is not drawn. `DSColorView` is the swatch and the value, the swatch alone, and the empty case. `DSProgressCircle` is the ring at each size, filled to a value and turning. `DSMark` holds `shape`, `variant`, `size` and `scaleSize` as properties, and `color` as a mode. `DSConfirmPopover` is its surface alone, with the question and the two actions, and the control that opens it is not part of the drawing. `DSConfirmDialog` is its surface alone, over `DSBackdrop`.
- **A cell the library plans and a unit's Main page does not draw is a gap of the showcase, and it is fixed on the unit's page before its library page is read** (`RULE.SUPPORT.SURFACE.446` · MUST · skill:spn-surface/design). Hover and pressed, which no page holds, are driven on the case rest of the unit in the library (`RULE.SUPPORT.SURFACE.445` · MUST · skill:spn-surface/design). A part of a unit that is another unit is an instance of that unit's set, at the version its props give, with its record's words, icon and size as overrides, and a part no version matches stays as its record drew it and is reported (`RULE.SUPPORT.SURFACE.447` · MUST · skill:spn-surface/design). Heading: "The path of a page through the connector".
- **A unit's section holds its Main page's sections by name, and a page is one group of the showcase** (`RULE.SUPPORT.SURFACE.032` · MUST · skill:spn-surface/design). A section is named as the unit and holds, from the top, where it lives, its header, then Usage, Sizes, Levels, Colors, Looks, Content, Data, States and Parts, each under its label, with the set in Sizes. A page's name is its group's name read from the showcase's title without `Components/`, and the pages stand in the showcase's order. Heading: "A unit is one section".

## The walk, in order: the path of a page

**Before the first connector write, read the `Theme-Font` variables `text`, `display` and `code` of the core file, and read `figma.listAvailableFontsAsync()` for the three families they name.** A family whose font Figma hosts (Geist, Geist Mono and Schibsted Grotesk) needs nothing. A brand font that Figma does not host is uploaded by the person under its own name, in Figma's account settings, and the variable is set to that name; if anything is missing, or anything else of the setup is, read `skills/design/steps/setup-figma.md` and run it with the person. Draw nothing until all three families are listed. The connector sees the fonts Figma hosts and the fonts uploaded to the person's Figma account, and none installed only on the machine, so its list is the check.

A page of a library file is one run of the steps below, in this order, and each page is read back before the next page starts. Heading: "The path of a page through the connector".

1. **Ask the developer for a named version before the first change in the file, and wait.** The connector cannot save one. Heading: "Before a connector writes".
2. **Plan the page from the held snapshot.** Read the page's units and planned cells from the CONSTRUCT snapshot the tool holds, and plan no cell from the file. Heading: "The path of a page through the connector".
3. **Read the page's cells into records.** Run `spnutils apps surface record <file> --page <page>`. It reads each planned cell from the showcase's Main pages into the unit's record, in light and in dark, lists what Main does not draw, and prints the page's units in the order they are drawn in. A cell Main does not draw is fixed on the unit's showcase page first, and the page is read again; hover and pressed are the exceptions, which no page holds. Heading: "The path of a page through the connector". A record holds what the web draws, as the browser decides it: an element shown to a screen reader only is no layer, an element taken out of the flow keeps where it stands and is drawn out of the auto layout, and a value the web types with no token is drawn at that value and named typed. A narrow cell is read in a page-wide viewport, with a unit that fills its place held to the width its page gives it.
4. **Know the file's page model before you draw.** A library file follows the showcase's page model: a page for each group, a section for each unit, its header, then Main's sections by name, the set in Sizes with one component for each version, each prop the set does not cross a property of the set, each case an instance with its properties set, and each part that is another unit an instance of that unit's set. The frames are named as the arranged form states. Heading: "A unit is one section" and "The arranged form".
5. **Draw each unit from its records with the plugin's code, run through the connector.** The plugin's code is `connector.png`, which `spnutils apps surface figma` writes beside `code.js` in the plugin folder. Upload it with `upload_assets`, then one `use_figma` call reads the PNG from the uploaded image's bytes, evaluates the gunzip in its `nInf` chunk, evaluates the gunzipped `nBdL` chunk, and calls `globalThis.__spn.arrangeUnit(cfg)` with the unit's plan and its record. Draw the units in the order step 3 printed. The code draws every cell from its record, each layer an auto-layout frame with the record's layout, boxes and texts, binds every paint by its token to the published variable of DS 1-Core and every text to the `Theme-Font` variables, draws each icon from the core's shape, and makes the set's versions components with every other cell an instance. Each part that is another unit becomes an instance of that unit's set. `unmatchedParts` in the answer lists what stayed as its record drew it, and each is reported, never fixed by hand. Heading: "A unit is one section" for the parts, and "The path of a page through the connector" for the order.
6. **Run `spnutils apps surface gaps` on the page's units, for the showcase and for the file.** It compares the drawn cells with their records and the book, and names each drift at level 3: a column's share, a text's family, size or weight, a gap or a padding, a paint's variable. Fix each gap in the plugin's drawing (or the record, or the plan), draw the unit again, and run `gaps` again. Never repair a difference by hand in the file. Heading: "The path of a page through the connector".
7. **Remove what an earlier way of drawing left on the page.** A frame the page holds that no unit's section owns is removed by its id, and each removal is reported.
8. **Read the page back against its plan.** Compare each section of a unit with its planned cells through the connector: the set by version, every other cell by instance and props, every paint by the variable it is bound to. A section that holds a cell the plan does not name, or lacks one it does, is a difference, and so is a paint bound to no variable. Report each with its unit, its section and its cell, correct the plan, the record or the plugin's drawing, and draw the page again. Heading: "The read-back of a page".
9. **Tell the developer what changed, what still differs from the web and was left, and that the publish is theirs.** The developer publishes after the last page is read back.

- **Units that do not depend on each other may be drawn in parallel, each by its own run.** Every page is read into records at once, and a unit is drawn only after every unit it is built from that the same file holds. Each run follows the steps in order, and touches only its own units' sections, its own drawn cells and its own holder node. A call that changes what runs share, such as the variables, the text styles, the order of a page's sections, a part in Shared parts or the cover, runs alone. Heading: "How the connector's work is carried out".
- **Where a library file has taken a library's update, read its sets again and read the page back again before you say anything is whole.**

## After the last page

Before you tell the developer anything is whole, close the loop against the code yourself, and scan the file once. Headings: "Before a publish", and "The connector's facts", under A library's update.

1. **Read the file again, and take it in.** Read each page you changed with `skills/design/scripts/inventory.js` (the list of pages first, then one call for each page) and `skills/design/scripts/tokens.js`, save each answer as a file in one folder, put them together with `node skills/design/scripts/assemble.mjs --answers <folder> --out <inventory>`, and take that in with `spnutils apps surface library --file <inventory>`. Where the inventory is for an agent's own work, `skills/design/scripts/page.js` reads one page, with the time of the reading written on it. Prove each unit by a hash: send the same script again inside a function with its body unchanged, have it return an eight-character hash for each unit, compute the same hash from the answer file, and compare by program. Headings: "The inventory", "How the connector's work is carried out", and "What the agent reads and keeps".
   - **`page.js` stops by its byte limit on a large page.** It answers what fits under `maxBytes` and names where to go on in `next`: at `maxBytes` 15000 to 16000 one answer held 49 to 70 nodes, of pages of 88 to 367. Read the rest with a short read-only script of your own, limited to the section you work in, and do not send `page.js` for range after range. `page.js` gives no key, no mode and no binding, so the same short script reads those.
   - **`page.js` and the scan do not see a component that stands inside a plain frame.** Their walk goes down through sections and no further, so the 56 icons of the Core file's Icons page count as one reference frame. Read such components by their ids.
   - **`assemble.mjs` refuses a folder with no answer of `tokens.js`.** Read `tokens.js` for every library file, also one that holds no variable and no style, whose answer says `itemCount` 0. With `--out` inside the answers folder, a second run would read the inventory as an answer, so assemble a folder once.
2. **Run `spnutils apps surface gaps <package>` for the stack the unit belongs to.** A unit you just drew that still shows as a gap means the drawing did not match what the stack's own snapshot expects: read the gap and fix the plugin's drawing, the record or the plan, not the stack, unless the gap is a real difference you are telling the developer about.
3. **Scan the whole file last, a page at a time, with the four parts of the scan: `skills/design/scripts/scan-labels.js`, `scan-placement.js`, `scan-properties.js` and `scan-sets.js`, each passed to the connector as it is with its inputs filled, one part for each call.** The scan is one scan cut in four so that no call nears the limit of 50,000 characters, and a part is never sent in a shape other than as it is; a page is clean when all four parts say `clean`, and `only: "<finding>"` asks a part for one finding whole. A part reads a page of either form (nodes at its top level, or inside sections) and says which in `form`; inside a unit's section it reads the arranged form, the header (`header · <Unit>`, a text or a frame of texts) and `body · <Unit>` with Main's sections in order, walking through the frames named `body · `, `section · `, `sub · `, `row · `, `cell · ` and `set · `, so those names are the ones the arranging must give; a page where it found no unit answers `emptyReading`, never `clean`. A scan part only reads, so one that comes back as anything but its own answer is sent once more, whole, in a reply of its own; if the second sending fails too, write "not read" for that part and go on. Heading: "Before a publish".
   - **On a page of the Core file only `scan-labels.js` answers `emptyReading`.** `scan-placement.js`, `scan-sets.js` and `scan-properties.js` answer `clean: true` there having read no unit, because the scan stops at a plain frame. Do not take that `clean` for a reading.
   - **No scan part reads the order of the layers panel.** Read `page.children` and each section's `children` yourself: the panel reads from the last child to the first. A section out of the showcase's order on the page is moved first, by its exact id.
   - **A page is clean when all four parts say `clean`;** a part not read is not clean, and the page is reported as not fully read. Report page by page: for each part, clean or not, every finding that is not 0 with its name, its count and the ids and names the scan gives, and how many sendings the part took.

## The measure and the pace

- **A library is brought to the web by its properties, its values, its defaults and its states, and by nothing clipped or overlapping.** This is the book's own rule: "A property that changes what is visibly there is drawn", and a state a unit can be in is drawn. Anything finer than that is listed in the report and not drawn. The developer decided this on 2026-10-09.
- **A page is read back when it is arranged, and the file is scanned once, when every page is done.** A read-back after each unit costs a read of the page each time and proves what the arranging already returned.
- **What a writer reads before its first call is paid for by every writer.** A writer that is handed `skills/design/steps/writer-brief.md` and its order reads two pages, and it opens a long step only when it is stuck. Measured on DS 2-Components on 2026-10-13: two writers that were handed the brief and one order used 164 and 167 thousand tokens, and writers that were handed six documents to read whole used 350 to 750 thousand tokens on rows of the same size.
- **The model of a child follows its work.** Work that its order states whole goes to the smaller model: a check and an inventory. The developer agreed to this on 2026-10-13.

## A child agent

A child agent that sends `use_figma` cannot read the connector's own skill, so this skill carries the rules a child needs.

- **Hand a writer `skills/design/steps/writer-brief.md`, the order for its work and the file's inventory.** The brief restates what a writer of one page needs from `skills/design/steps/connector-rules.md` and from this walk. The writer opens one of those only when it is stuck, which is when it meets a thing the brief does not cover or a call fails in a way it cannot explain. Its report says which step it opened and why. The order names what the brief leaves to it: the page, its units and its holder node, the records it draws from, and the path of its report.
- **Hand `skills/design/steps/connector-rules.md` whole to a child whose work the brief does not cover.**

A child sends nothing the order does not name.

Never edit the body of any script: fill its inputs and pass the rest as it is.

Keep the inventory current as you go: a change to the file updates the inventory's lines for what it changed.

**The connector cannot publish a library, and it never does.** The developer publishes after your word.
