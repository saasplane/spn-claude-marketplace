# Session — the refusal is written and the credential is not

**Source of truth:** the foundation's `docs/04-capabilities/02-support/02-infra/10-providers/gcp/03-session.md`. Read this as the restatement; that node governs.

**Nothing here states which session values a Google Cloud run would read**, because no run reaches a Google Cloud account.

**What to do instead.** There is nothing to authenticate against. A plan reaches no account and needs no credential, so a cloud walk can be rehearsed before any account exists. An apply against this cloud does not exist to be approved.

**Why this is a ruling rather than an absence.** The credential check reads the provider the estate declared, and nothing in the driver names a vendor ([trust](../../trust.md)). A probe for this cloud's own variables written here would put vendor knowledge above the blueprint line, which is the defect the law forbids.

## What is true today

**The shape of the refusal is already decided.** The check expects the declared provider's own session values and refuses by naming that provider when they are absent. An estate declaring Google Cloud would be told which provider's session was wanted.

**That rule was written from this exact failure.** A credential posture type was built and withdrawn the same day because it probed one vendor's variables: a session holding another cloud's credentials read as a rehearsal, which fails safely and is still wrong (`RD.SUPPORT.INFRA.094`).

**So this cloud is already covered by the law it has no realization for.** What is missing is a run to hold a credential, not a rule about holding one.
